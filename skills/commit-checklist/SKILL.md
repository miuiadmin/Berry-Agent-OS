# 提交前自查

替用户执行 git 提交前，按序过完四步。任何一步不过即停下解决，不带着问题提交。

## 1. 跑项目的验证命令

- 先看项目根的 AGENTS.md / README / package.json scripts，找到该项目约定的验证命令（测试、类型检查、lint 等），跑相关的子集——本次改动触到的面必须绿。
- 不确定哪些相关时，跑全量测试套件；跑不动（超时/环境缺）就明说哪部分没验证，不假装验过。
- 测试红 = 修好再提交；跳过红测试提交是禁止项。

## 2. 核对改动清单

- `git status` + `git diff`（含 staged）通读一遍：每个文件都答得上「为什么它在这次改动里」。
- 答不上来的文件（顺手改动、编辑器副产物、无关文件）剔出去，不混进本次提交。

## 3. 逐文件点名暂存

- 用 `git add <明确路径>` 逐个加文件，不用 `git add -A` / `git add .`——全量暂存会把不相关或意外文件卷进来。
- add 完再 `git status` 核一遍：无意外文件混入、无该加而漏加的文件（`??` 残留）。

## 4. 提交

- 一次 commit = 一个逻辑完整的变更；多个不相关改动拆成多笔。
- commit message 说清「做了什么、为什么」；遵循项目已有的 message 风格（看 `git log` 近几笔）。
- 提交后 `git log -1 --stat` 回看一眼：文件清单与预期一致。

## 红线

- 别人工作区里的进行时文件（测试 fixture 未落、格式未跑）出现在 status 里时，只提交属于自己的改动，不替别人收尾。
- 项目声明的 gitignore 目录（设计文档类）永不 `git add -f` 强加。
- 提交是外显动作：用户只说「改好」没说「提交」时，先问一句。
