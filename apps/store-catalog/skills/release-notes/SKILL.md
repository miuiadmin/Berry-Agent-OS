# 发版说明整理

从一段提交历史整理面向用户的发版说明。

## 步骤

1. 取历史：用户给版本区间就看 `git log <区间>`；没给就看最近一次 tag 以来的提交，并说明采用的区间。
2. 分拣三段：
   - **新功能**：用户能做以前做不到的事；
   - **修复**：以前不对的现在对了（说现象不说实现）；
   - **破坏性变更**：升级需要用户动作的任何变化（配置面/API/命令行为/数据格式）。
3. 用户视角措辞：写「现在可以用 X 做 Y」，不写「重构了 Z 模块」——内部重构用户无感就不进说明。
4. 杂务提交（chore/CI/依赖升级无行为变化）归并成一行或不提。

## 输出形态

```markdown
## <版本号>（<日期>）

### 新功能
- …

### 修复
- …

### 破坏性变更
- …（无则省略本段）
```

## 边界

- 提交信息看不懂意图的，先查关联改动再归纳，仍不确定就不写（宁缺勿错）；
- 不夸大：小改进不写成「全新能力」；
- 版本号由用户拍板，说明里留占位不代填。
