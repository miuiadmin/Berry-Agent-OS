# 代码评审清单

对一段改动（工作区 diff 或指定提交范围）做结构化评审。

## 四维清单（按序过，先架构后细节）

1. **结构**：改动是否顺着既有架构走？有没有为局部方便引入新概念/新分支路径（补丁式代码）？删掉这段代码，系统的概念数量是增是减？
2. **边界**：跨模块依赖是否走正规接口？输入校验在哪一层执法？错误是否在正确的层被处理而不是被吞？
3. **错误处理**：失败路径是否 fail-loud（响亮失败优于静默降级）？资源是否在失败路径也正确收口（dispose/finally）？
4. **测试**：修 bug 是否带回归锁（修复前必红）？新分支是否被至少一个用例钉住？测试是否 mock 了中间层（假信心信号）？

## 输出形态

按严重度分级输出意见，每条带文件与行号定位：

- **blocker**：必须修才能合（错误行为/数据丢失/安全面）；
- **建议**：应该修但不阻塞（可读性/一致性/小幅简化）；
- **记档**：不必动但值得知道的（未来风险/风格差异）。

零意见时明确说「四维过完无 blocker」——不说「看起来不错」这种无法验证的话。

## 边界

- 只评审给到的改动面，不顺手扩到全仓（除非改动明确波及）；
- 意见基于代码事实，引用具体行；推测性的担忧标注「未验证」；
- 不改代码——评审产物是意见清单，改不改由用户裁决。
