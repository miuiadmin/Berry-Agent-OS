# 运维手册

> 数据目录、备份、清理、双开护栏、故障排查。全部操作以 operator 身份执行；删除类动作不可逆，先备份。

## 1. 数据目录布局

缺省 `~/.berry/`（`APP_DATA_DIR` 覆盖）：

```
~/.berry/
├── sessions.db              # 唯一 SQLite 库（WAL 模式）
├── sessions.db-wal / -shm   # WAL 附文件（运行期存在，正常）
├── overlay.yaml             # 组合树覆写（缺省不存在 = 官方默认层）
├── project-aliases.json     # 项目根别名表（缺省不存在 = 零重定向；形如
│                            #   { "现根绝对路径": "记账根绝对路径" }——项目目录改名/移位后
│                            #   配它，记忆与项目域键续用旧根——见 §7 故障排查）
├── allowlist.json           # 审批对 allowlist 持久面（缺省不存在 = 首次落 allowlist 决策时建）
├── skills/                  # 技能目录（每子目录一份 SKILL.md）
└── apps/                    # 应用面三布局：装机子树 + 各行数据根
    ├── node_modules/        # npm 装机子树（--legacy-peer-deps --omit=peer）
    ├── git/                 # git 源克隆子树 + sources.json（源 URL/ref 记录）
    └── <行id>/              # 各应用行数据根（data.json 认领桥与词表账本；
                             #   内含 tmp/ 子目录 = 件临时空间）
```

会话按**启动目录**归属：换目录即换会话序列。当前目录有哪些会话、续接哪条，由库内 sessions 表按 cwd 记录。

启动清扫：宿主每次启动会扫全体 `apps/<行id>/tmp/`，删除其中 mtime 超过 **7 天**的文件并剪除空目录（固定常数，无配置项；另一 berry 实例启动也会触发——含本实例运行中的场合）。这是件临时空间的 GC 语义：`tmp/` 无持久保证，件的正式数据放数据根其余位置，不要落 tmp。例外：`berry dump-config` 诊断命令（`:memory:` 库零落盘装配）不扫——清扫只在真实数据目录 + 持久库档的启动路径发生。

迁移规则：**只前进不回退**。库内 `user_version` 高于当前二进制所知 = 拒绝打开（宁拒绝不误读）——用旧版本打开新库会直接报错，这是设计行为不是故障。

## 3. 备份

```bash
# 方法一（推荐）：停进程后整目录拷贝
cp -a ~/.berry ~/.berry.backup-$(date +%Y%m%d)

# 方法二：运行期 SQL 备份（含 WAL 合并，得到一致快照）
sqlite3 ~/.berry/sessions.db ".backup '/tmp/sessions-backup.db'"
```

不要只拷 `sessions.db` 而丢 `-wal`：运行期的最新写入可能还在 WAL 里。

方法二只备份数据库；`overlay.yaml`、`project-aliases.json` 等目录内配置文件不在 SQL 快照里——完整恢复请用方法一（整目录），或在方法二之外单独保存这几个文件。

注意：`credentials` 表存 provider 凭证（明文形态 + 数据库文件 0600 权限 + 预留加密 seam，pre-release 拍板）——**备份文件即含密钥**，备份产物按密钥保管（加密盘/受限权限），不要进同步盘或公开位置。

## 4. 清理与重置

按破坏性从小到大：

```bash
# 只清记忆（保留会话与技能）：memory_fts 是投影会自动跟随
sqlite3 ~/.berry/sessions.db "DELETE FROM memories; DELETE FROM memory_fts;"

# 只清跨会话检索索引（可重建，重启后自动对账补齐）
sqlite3 ~/.berry/sessions.db "DELETE FROM session_fts; DELETE FROM session_fts_state;"

# 清全部会话历史（保留记忆/goals/凭证/技能）
sqlite3 ~/.berry/sessions.db "DELETE FROM events; DELETE FROM sessions; DELETE FROM goals;"

# 整库重置（全新开始）
rm ~/.berry/sessions.db*
```

删除会话是 operator 动作——没有插件 API 能删会话（跨会话只读面故意无 delete 词汇）。

## 5. 双开与多机护栏

允许两个进程同时开（不同目录或同目录）：

- **WAL 模式**：读写不互斥，各进程经 WAL 看到彼此提交。
- **同会话单写者护栏**：会话头带 `incarnation:revision`，旧 incarnation 对已换代会话的写入会被拒——双开续接同一会话不会写花。
- 最稳的姿势仍是**一目录一进程**。

多机与网盘的边界（明示不支持，不是缺陷是立场）：

- Berry 是**单 operator 单活跃机**的个人系统：同一数据目录同一时刻只应有一个机器在写。
- 多机使用的正确姿势 = **单活跃机 + 他机只读冷备**：在他机上消费停机拷贝的备份（§3 方法一的产物），不做实时双活。
- **数据目录放网盘/云盘同步（Dropbox / iCloud / NAS 实时同步等）明示不支持**：SQLite 的 WAL 一致性协议建立在普通本地文件系统语义上，跨网络文件系统必然损坏——库损坏是文件系统真相，不是可修的 bug。备份产物进网盘没问题（它是静态文件），活跃库不行。

## 6. 日志

- 级别 `APP_LOG_LEVEL`（debug/info/warn/error）；`npm run dev` 缺省 debug。
- 进程日志只是观察面：审计与回放的权威载体是库内 durable 事件（`events` 表），不是日志文件。
- 排查应用装载：`berry dump-config`（只读不落库）——合成树、每行 activated/failed/skipped/unresolved 及原因一次看全。

## 7. 故障排查

| 症状                                               | 原因与处置                                                                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动即拒：`user_version` 高于已知                  | 库被更新版本写过。用对应新版本二进制打开，或备份后整库重置。不降级是设计行为                                                                                                                                                                                                                                                                                                  |
| 启动断言：应用失败行清单                           | 某件 apply 抛错 / 配置不过 schema / 入口缺失。`dump-config` 看行级原因；修 overlay（`disabled: true` 先隔离）；`APP_ENTRY_UNRESOLVED` 行需 `/apps-install` 装机 + `/apps-mount <装机id> --apps <应用id>` 挂载（两态：装机零生效，写行才进组合树）                                                                                                                     |
| 坏件锁死启动（TUI 起不来）                       | 安全模式自救：`berry --no-apps` 起最小内核（组合树空装只留 Ring 1 硬装配——TUI 无对话驱动但命令面/应用管理完好），修好 `overlay.yaml` 后 `/reload` 恢复全树；旗标只影响本次 boot，`/reload` 读盘不受它约束。`berry dump-config --no-apps` 同径看安全模式树                                                                                                               |
| `SESSION_FORMAT_UNSUPPORTED`                       | 读到了未知事件类型且非 ignorable——通常是用旧版本读新插件词汇写的库。用写它的那个版本组合打开                                                                                                                                                                                                                                                                                  |
| 会话「丢」了                                       | 会话按 cwd 归属。回到原启动目录启动即续接；或查 `sessions` 表按 cwd 找                                                                                                                                                                                                                                                                                                        |
| 记忆检索变慢                                       | `session_fts` 水位落后属正常（激活期对账 + 运行期增量）；重启自动对账补齐                                                                                                                                                                                                                                                                                                     |
| Ctrl+C 没退出                                      | 多会话在跑时首次 Ctrl+C 是**打断聚焦会话的 run**（aborted 终值、不退 OS）——用 Ctrl+D 或 `/quit` 退出；单会话形态首次即优雅退出（等在途 run 结算），再按一次立即 130                                                                                                                                                                                                           |
| 子代理任务卡住                                     | `/apps` 确认 subagent 行激活；Job 结算通知走 ui 三通道，看通知器；进程退出时 shutdown 序列会排空 jobs                                                                                                                                                                                                                                                                      |
| 卸载提示行不在 / 「无动作」                        | `/apps-uninstall <id>` 裸调先检视（受影响会话计数与数据域体积在报告里），`--confirm` 才执行；回执「无动作」= 行不在且无残迹（已卸载过或从未安装），「残迹收尾」= 上次段间失败的收敛重跑——两者都是幂等合法终态非错误。Ring 1 底座行（当前 = tools）拒卸是设计行为                                                                                                            |
| `/reload` 没立即生效                               | run 进行中不拒而是排队——本次 run 结算后自动执行一次（连发合并），结果另行通知；失败时原组合仍在运行，修 overlay 后重试                                                                                                                                                                                                                                                        |
| 项目目录改名/移位后旧记忆不见                      | 记忆按 canonical 工作区根记账，根变了即新键。在 `<数据目录>/project-aliases.json` 配 `{ "现根绝对路径": "记账根绝对路径" }`（键 = 移动后的新路径，值 = 原路径），重启后 canonical 根重定向，续用旧记忆                                                                                                                                                                        |
| 分域行（worker/external 载体）崩溃 / OOM           | 该域死不伤宿主（故障域分域）：行状态转 failed（`/apps` 可见，与 `app/failed` 广播同源），**不自动重启是设计行为**——修好后 `/reload` 重装载。第一手死因在结算消息里（OOM 签名 = `reaching memory limit`，另有 `worker/oom` 活体事件；内存档 = 应用清单 `budget.memoryMb` 或宿主缺省 512MB——只限 JS 引擎堆）。`dump-config` 组合树带 `@worker` / `@external` 载体标注可核对行归属域 |
| 分域行卡死无响应                                    | 心跳丢拍（缺省 15s × 3 拍 ≈ 45s）判冻结 → watchdog 自动 kill 走意外死亡结算（`worker/froze` 事件）。装载期慢**不是**冻结——boot 冷启窗归 load 超时监督，两窗分治不互借判据；挂起族可判可杀、CPU 燃烧不可判（如实收窄）                                                                                                                                                         |
| `--sandbox-host` 退出码 1（`SANDBOX_UNAVAILABLE`） | fail-closed 设计：平台无沙箱后端即拒跑——Windows 无后端；Linux 需安装 bubblewrap（Ubuntu 23.10+/24.04 需先放行 userns，三法见 §7.1）；macOS 用内建 seatbelt。不是 bug：去掉旗标即可跑，或在受支持平台/装好 bwrap 后再用。沙箱内可写面只含档位根与数据目录，报写入错误先核这两处                                                                                                                                                    |
| 分域行调用报 `BRIDGE_SURFACE_NARROWED`          | 设计行为非故障：分域行（worker/external 载体）五个 ctx 同步编排面（`parallel`/`serial`/`waterfall`/`registerMessageRole`/`registerSessionEventType`）不开放，服务调用是 RPC Promise 唯一形态——件编排逻辑改走服务调用 + 事件订阅（作者须知见[应用开发指南](应用开发指南.md)）                                                                                                                     |

### 7.1 OS 沙箱后端部署（三平台）

`--sandbox-host` 宿主沙箱与 exec 沙箱三档共用平台后端，部署事实分平台如下（fail-closed：后端不可用即拒跑，不静默降级）：

- **Linux（bubblewrap）**：Ubuntu 23.10+/24.04 起 AppArmor 默认限制非特权 user namespace，**bwrap 开箱即坏**（典型症状：bwrap 自报 "bwrap: setting up uid map" 类错误、工具执行以 `EXEC_SPAWN_FAILED` 响亮失败——`SANDBOX_UNAVAILABLE` 只出现在 `--sandbox-host` 启动期后端链为空/探测全败的路径，不在 exec 执行期〔冷读闸 2026-08-29 勘正：单候选链构造期不预探测〕）——这是发行版安全策略，不是 Berry 的 bug。放行三法任选其一：
  1. **系统级放开**：`sysctl kernel.apparmor_restrict_unprivileged_userns=0`（写入 `/etc/sysctl.d/` 持久化）——最简单，代价是全系统放开该限制；
  2. **自定义 AppArmor profile**：仅对 bwrap 二进制授予 user namespace 权限（`userns,` 规则）——最小面放行，推荐多用户/在意攻击面的机器；
  3. **setuid 安装的 bwrap**：改用带 setuid helper 的 bubblewrap 构建/发行包——setuid 路径不依赖非特权 userns。
- **macOS（seatbelt）**：使用内建 `sandbox-exec`。Apple 将其标记废弃已近十年但**至今仍工作**，且无官方 CLI 替代（同类工具同依赖此路径）；若未来 macOS 版本实际移除，届时按 `SANDBOX_UNAVAILABLE` fail-closed 拒跑并跟进替代后端。
- **Windows**：当前无 OS 沙箱后端（`--sandbox-host` 直接 fail-closed）；write-restricted token 路线已在进程隔离规划中立项，落地前 Windows 平台不带 `--sandbox-host` 运行。

诚实边界一条（PoC 实证，CVE-2026-21711 同型）：external 分域行的 Node permission-model 中层只管文件系统路径访问与 addon，不管 `bind()` 创建 Unix domain socket 文件这条 syscall 路——实测写白名单外目录的普通文件被拒（`ERR_ACCESS_DENIED`）而同目录 UDS bind 通过。因此 PM 是叠加的中层、不是墙：external 域的执法面 = 进程墙（per-行 fork）+ OS 沙箱层（宿主基线 ∩ 行声明交集）；白名单内目录的 UDS bind + 回环通信正路可用（域 IPC 选型不受此判影响，判的是越界 bind）。

## 8. 升级

1. 备份（§3）。
2. `git pull && npm install && npm run build`。
3. 首次启动自动跑迁移链（`user_version` 前进；DDL 与版本号同事务，无半迁移状态）。
4. 应用行 `unresolved`：官方件随包不存在此问题；文件件按 `/apps-install` 重装后 `/apps-mount <装机id> --apps <应用id>` 重挂（两态键域：装机与挂载两步）。
