# 智能体 2.0 进化 — AI Agent 团队管理平台

> 基于 BerryAgent 扩展的多租户 AI Agent 团队协作平台，参考 Multica 架构设计。

---

## 一、产品愿景

一个人管理多个 AI 公司/团队，像管理真实企业一样：建组织架构、分配任务、看板追踪、定时调度、链式协作。**核心交互方式是对话** — 用户通过跟一个全局助手对话来打造和管理所有团队。

### 核心概念

**一个人 → 全局助手（对话入口）→ 多个公司（团队）→ 多层级 AI 组织 → 看板驱动执行**

```
用户（你）
└── 🤖 全局助手（用户级，每人一个，对话总入口）
    │
    ├── 公司 A（内容团队）
    │   └── 🧠 1号负责人（自动生成）
    │       ├── 中心：内容运营中心
    │       │   ├── 系统：短视频系统
    │       │   │   ├── 部门：脚本部
    │       │   │   │   ├── 组：创意组 → [Agent1, Agent2, Agent3]
    │       │   │   │   └── 组：审核组 → [Agent4, Agent5]
    │       │   │   └── 部门：制作部 → [Agent6, Agent7]
    │       │   └── 系统：图文系统 → ...
    │       └── 中心：技术中心 → ...
    ├── 公司 B（开发团队）
    │   └── 🧠 1号负责人
    │       └── ...
    └── 公司 C（研究团队）
        └── 🧠 1号负责人
            └── ...
```

### 全局助手（对话总入口）

**定位：用户的智能代理人 — 通过对话统领一切**

```
全局助手不是"所有负责人的上级"，而是"用户的化身":

  用户说话 → 全局助手理解意图 → 路由/委托/直接处理

  它的角色类比:
    · 全局助手 = 你的私人秘书/CEO 办公室主任
    · 团队负责人 = 各子公司 CEO
    · 秘书不审核 CEO 的工作，而是帮老板传达指令、汇总信息、处理杂务
```

**全局助手的能力:**

```
1. 建团队（AI 建团队的对话入口）
   用户: "帮我建一个内容营销团队"
   → 全局助手引导对话 → 生成组织架构 → 创建 workspace

2. 路由委托（识别意图，分发到对应团队）
   用户: "帮我写一篇小红书"
   → 全局助手判断: 这是内容团队的活
   → 委托给公司 A 的 1 号负责人
   → 负责人在团队内正常拆解/指派/审核
   → 结果返回全局助手 → 呈现给用户

3. 跨团队汇总
   用户: "这周所有团队干了什么"
   → 全局助手聚合各团队数据 → 生成汇总报告

4. 全局管理
   用户: "把开发团队的 Agent X 移到内容团队"
   → 全局助手执行跨团队操作

5. 直接对话（不涉及具体团队时）
   用户: "帮我翻译这段话" / "今天天气怎样"
   → 全局助手自己处理，不委托
```

**全局助手与团队负责人的关系:**

```
┌─────────────────────────────────────────────────────────────┐
│  关系类型: 委托，不是上下级                                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  · 全局助手不审核负责人输出（负责人直达用户）                    │
│  · 全局助手只做路由/传话/汇总，不做业务判断                     │
│  · 委托 ≠ 指派: 委托是"请这个团队处理"，不干预内部怎么做        │
│  · 负责人完成后结果回传全局助手 → 全局助手组织语言呈现给用户     │
│                                                             │
│  为什么不是"上级":                                            │
│    1. 如果全局助手审核所有负责人 → 变成全局瓶颈（正是我们要避免的）│
│    2. 全局助手是秘书角色，不懂各团队业务细节                     │
│    3. 负责人才是团队业务的最终决策者                             │
│    4. 用户才是真正的"审核者"，全局助手只是代理                   │
│                                                             │
│  数据关系:                                                    │
│    · global_agent.workspace_id = NULL（不属于任何 workspace）  │
│    · global_agent.superior_id = NULL                         │
│    · global_agent.agent_type = 'global'（特殊类型标识）        │
│    · 每个用户有且只有一个全局助手（注册时自动创建）              │
│    · 全局助手有自己的记忆系统（跨所有团队的全局记忆）            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**委托流程:**

```
用户: "帮我写一篇关于 AI 的小红书文案"
  → 全局助手 Brain 分析意图:
      · 任务类型: 内容创作
      · 目标团队: 公司 A（内容团队）
      · 信心度: 高（用户只有一个内容团队）
  → 全局助手创建委托:
      · 调用内部工具 delegate_to_team(workspace_id, prompt)
      · 在公司 A 的 1 号负责人会话中发起对话
      · 等效于用户直接对负责人说这句话
  → 负责人接手（对负责人来说就像用户直接说的）:
      · 拆解任务 → 指派下级 → 审核 → 汇总
      · 完成后结果回传
  → 全局助手收到结果:
      · 组织语言: "文案已经写好了，这是内容团队的产出: ..."
      · 呈现给用户

特殊情况:
  · 用户有多个团队能处理 → 全局助手问: "要交给哪个团队？"
  · 需要多团队协作 → 全局助手分别委托 → 汇总结果
  · 用户指定了团队 → 直接委托，不猜
  · 任务不属于任何团队 → 全局助手自己处理（或建议建新团队）
```

**用户仍可直接跟任何 Agent 对话:**

```
全局助手是"默认入口"，但不是唯一入口:
  · 默认对话: 打开 App → 跟全局助手聊（最自然的方式）
  · 直接对话: 进入某团队 → 点击某 Agent → 直接对话（跳过全局助手）
  · 两种方式结果相同: 都经过上级审核链
  · 区别: 全局助手会帮你路由，直接对话需要你自己找到正确的 Agent
```

**全局助手降级策略（路由层故障兜底）:**

```
全局助手依赖 LLM 做意图识别和路由。当 LLM 调用失败时:

  降级策略（逐级）:

  第 1 步: 重试（自动）
    → 指数退避重试 2 次（3s, 9s）
    → 重试成功 → 正常路由

  第 2 步: 前端 fallback 手动路由
    → 2 次重试均失败 → 前端弹出"手动选择团队"面板
    → 展示用户的所有 workspace 列表
    → 用户选择目标团队 → 消息直接发送给该团队负责人
    → 等效于用户跳过全局助手，直接跟负责人对话（路径 1）

  第 3 步: 关键词匹配降级路由（可选）
    → 若用户开启了"快速路由"设置
    → 基于历史路由记录建立简单映射:
        · 最近 30 天，"写文案/小红书/抖音" → 80% 路由到 workspace A
        · 匹配到 → 直接委托，不经 LLM
    → 匹配不到 → 回退到第 2 步

  设计约束:
    · 降级路由不使用 LLM（纯规则匹配或用户手动）
    · 不默认启用关键词匹配（避免误路由）
    · 降级期间全局助手仍可处理非委托类请求的 fallback:
        跨团队汇总 → 提示"路由暂不可用，请稍后重试"
        建团队 → 同上（必须 LLM，无法降级）
    · 直接对话路径（路径 2/3）完全不受影响
```

### 三个核心设计原则

**1. 多公司（团队）管理**

- 一个人可以创建无限个公司/团队（本质是 workspace）
- 每个公司完全独立：独立组织架构、独立看板、独立文件空间
- 可以理解为"公司 = 团队 = workspace"，叫什么都行，用户自定义

**2. 无限层级组织树（AI 生成，非硬编码）**

- 树形结构不是死代码，层级名称是 AI 标签/AI 归类/AI 生成
- 想有多少层就多少层：组 → 部门 → 系统 → 中心 → 公司，或者完全自定义
- 类似二叉树/多叉树：3 个 Agent 的上级是 1 个 Agent，这个 Agent 又有上级
- 用户可以通过对话描述需求，AI 自动生成整棵组织树 + Agent 角色配置
- 也可以手动在前端拖拽创建/调整

**3. 每个 Agent 都有自己的 Brain（三级架构内化）**

原 BerryAgent 三级架构完整内化到每个 Agent 内部：

```
┌─────────────────────────────────────────────────────┐
│  每个 Agent 内部都是完整的三级架构:                    │
│                                                     │
│  L1 Brain ← Agent 内部的审核/自纠错组件              │
│       ↕ 自审                                        │
│  L3 Conversation ← Agent 的对外交互层（用户/上级）    │
│       ↕ 按需调用                                    │
│  L2 On-demand ← Agent 内部的专业能力                │
│     · Learning  — 自动学习/记忆                      │
│     · Skills    — 技能进化                          │
│     · Code      — 代码执行                          │
│     · Tools     — 工具调用                          │
└─────────────────────────────────────────────────────┘
```

**关键设计：每个 Agent 有脑子，上级审核下级**

- 没有独立的 "Brain Agent" 实体 — Brain 是每个 Agent 的内部组件
- 用户可以跟任何 Agent 直接对话（通过 L3 对话层）
- Agent 产出结果后，由**直属上级**审核（只审一层，不层层审）
- 顶层 Agent（1号负责人，`superior_id = NULL`）的输出直达用户，无外部审核
- 创建 workspace 自动创建 1 号负责人 Agent

```
用户
  ↕ 可以跟任何 Agent 对话
Agent 1 (负责人, superior_id=NULL)
  ├── [内部: Brain + L2 + L3]
  ├── 输出直达用户（无上级审核）
  ├── 负责审核 Agent 2/3 的输出
  │
  ├── Agent 2 (组长)
  │     ├── [内部: Brain + L2 + L3]
  │     ├── 输出由 Agent 1 审核
  │     ├── 负责审核 Agent 4/5 的输出
  │     │
  │     ├── Agent 4 → 输出由 Agent 2 审核
  │     └── Agent 5 → 输出由 Agent 2 审核
  │
  └── Agent 3 (组长)
        ├── [内部: Brain + L2 + L3]
        ├── 输出由 Agent 1 审核
        └── Agent 6 → 输出由 Agent 3 审核

执行+审核流程:
  用户给 Agent 5 发指令
    → Agent 5 执行（内部 Brain 自审自纠）
    → Agent 5 输出 → 提交直属上级 Agent 2 审核
    → Agent 2 的 Brain 审核：通过/修改/退回
    → 通过 → 结果返回用户
    → 退回 → Agent 5 重做
```

**原三级架构 → 新平台的完美对应：**

| 原架构 | 新平台 | 保留方式 |
|--------|--------|----------|
| L1 Brain（审核者） | 每个 Agent 内部的 Brain 组件 | 自审 + 上级审核下级 |
| L2 On-demand（专业能力） | 每个 Agent 内置的能力层 | Learning/Skills/Code 自然存在于每个 Agent 内部 |
| L3 Conversation（执行者） | 每个 Agent 的对话层 | 用户可以直接跟任何 Agent 对话 |
| Brain 必审所有回复 | 上级 Agent 必审下级输出 | 审核权跟随层级，不再是全局单点 |
| AppCore 管理生命周期 | 平台调度器管理 | 升级为分布式调度 |
| IPC 通信 | 任务队列 + Electron IPC | 更解耦 |

**为什么这个设计更好：**
1. 每个 Agent 都完整 — Brain/L2/L3 全内置，完全自治
2. 审核分布式 — 上级审下级，不是全局瓶颈
3. 用户自由 — 可以跟任何 Agent 直接对话，不被 "Brain 入口" 限制
4. 像真公司 — 每个人有脑子、有能力、有上级审批，自然真实
5. 顶层 Agent 对用户负责 — 就像 CEO 对董事会汇报

**能力资源 × 组织层级 关系矩阵：**

```
组织层级:
  用户 (User)
    └── 全局助手 (Global Agent)
          └── 工作空间 (Workspace = 公司/团队)
                └── 组织节点 (org_nodes = 组/部门，纯分组标签)
                      └── 智能体 (Agent = 个体员工)

能力资源在各层级的归属:

┌──────────────┬──────────┬─────────────┬──────────────┬──────────────┐
│ 能力资源      │ User 级  │ Workspace 级│ org_node 级  │ Agent 级     │
├──────────────┼──────────┼─────────────┼──────────────┼──────────────┤
│ 记忆 Memory  │ global_  │ workspace_  │ —（不隔离）   │ agent_       │
│              │ memories │ memories    │              │ memories     │
├──────────────┼──────────┼─────────────┼──────────────┼──────────────┤
│ 插件 Plugin  │ plugins  │ plugins     │ —（不隔离）   │ plugins      │
│              │ (global) │ (workspace) │              │ (private) +  │
│              │          │             │              │ bindings     │
├──────────────┼──────────┼─────────────┼──────────────┼──────────────┤
│ MCP 工具     │ mcp-     │ mcp-bridge  │ —（不隔离）   │ mcp-bridge   │
│ (作为插件)   │ bridge   │ plugin      │              │ plugin       │
│              │ (global) │ (workspace) │              │ (private)    │
├──────────────┼──────────┼─────────────┼──────────────┼──────────────┤
│ 内置工具     │ bundled  │ —           │ —            │ 可通过       │
│ (作为插件)   │ plugins  │             │              │ bindings禁用 │
├──────────────┼──────────┼─────────────┼──────────────┼──────────────┤
│ 文件系统     │ —        │ shared/     │ —            │ workspace_   │
│              │          │ (团队共享)   │              │ path (私有)  │
└──────────────┴──────────┴─────────────┴──────────────┴──────────────┘

关键设计决策:
  · org_nodes 不参与能力隔离 — 它只是视觉分组，不是权限边界
  · 能力只在 3 层流动: Agent ↔ Workspace ↔ Global (User)
  · 插件是统一能力载体: Skills/MCP/工具/自进化全部走 plugins 表
  · 插件 scope 继承: global → workspace → private（三层合并或替换）
  · 记忆是"提升"模型（逐级向上推送），插件也支持 promote/demote
  · 向上提升需要确认（用户或负责人），向下可见是自动的
```

**4. 每个团队一个看板**

- 每个公司/团队有完整的看板系统
- 看板上显示：任务状态（待办/进行中/审核/完成等）、任务列表、各种评论
- 每个任务有：发起人（谁创建的）、责任人（谁执行的）、状态、优先级
- 任务可以由上级 Agent 指派给下级 Agent
- 执行结果、文件、讨论都在任务评论区里

### 功能清单

1. **全局助手** — 对话总入口，统领所有团队：路由委托、建团队、跨团队汇总、全局记忆
2. **多公司管理** — 创建任意数量的公司/团队，每个独立运作
3. **动态组织树** — AI 生成无限层级（组/部/系统/中心/自定义），标签化管理
4. **上级审核下级** — 每个 Agent 内置 Brain，直属上级全量审核下级输出，顶层负责人输出直达用户
5. **看板系统** — 每公司一个看板，任务含状态、发起人、责任人、评论流
6. **混合 Agent** — 内置 Agent + 第三方（Claude Code、Codex、OpenCode 等）
7. **上下级指令链** — Agent 只能向上汇报，上级向下指派、审核、纠正
8. **池认领模式** — 任务可按角色分配，多个同角色 Agent 负载均衡认领
9. **私有工作目录** — 每个 Agent 有独立 workspace（prompt、文档、代码、文件）
10. **团队共享文件夹** — 同团队所有 Agent 可访问
11. **多项目管理** — 每个团队可有多个项目
12. **评论与附件** — 任务评论区支持 Markdown、文件、执行结果
13. **AI 建团队** — 对话式交互描述需求 → AI 生成组织架构 + Agent 角色 + Prompt
14. **Cron 定时任务** — 定时触发 + 链式触发下级 Agent（结果经上级审核后再链式）
15. **Agent 自提醒** — Agent 可设置闹钟/提醒，到时自动执行
16. **Agent 自进化** — L2 learning 能力：自动提取可复用技能、积累记忆
17. **完整看板体验** — 拖拽排序、附件上传、评论流、状态流转
18. **执行断点恢复** — Agent 执行中断后可从 checkpoint 恢复，不必从头重做
19. **任务依赖关系** — 任务间 blocks/blocked_by，自动阻塞+解除
20. **验收标准** — 任务可设置结构化 acceptance criteria (checklist)，审核时参照
21. **Webhook/事件触发** — 除 cron 外支持 webhook、外部事件触发 Agent 执行
22. **并发策略** — 定时/自动触发重复到达时的策略 (queue/replace/forbid)
23. **批量操作** — 多选任务后批量移动/分配/删除/打标签
24. **多视图看板** — Board/List/Gantt/Timeline 多种视图切换
25. **任务反应** — emoji 反应（轻量互动，表态/确认）
26. **保存筛选视图** — 自定义筛选条件保存为命名视图，一键切换
27. **全局搜索** — Cmd+K 搜索任务/Agent/文件/命令
28. **错误分类重试** — 区分 transient/permanent/resource 故障，智能决定是否自动重试
29. **Skill 注入** — Agent 执行时自动将已习得技能注入 system prompt
30. **任务编号** — workspace 级自增编号 `PRJ-123` 格式，方便口头引用和搜索
31. **评论 Threading** — 评论嵌套回复、resolved 标记、按 thread 分组
32. **自动暂停保护** — 定时任务连续失败超阈值自动暂停 + 通知用户
33. **准入检查** — 触发前验证 Agent 在线/未归档/有能力，失败标 skipped 而非 failed
34. **通知订阅偏好** — 自动订阅(创建者/指派人/评论者)，per-group 可静音
35. **重复任务检测** — 创建前查重，防止并发创建相同任务
36. **任务自定义字段** — per-task metadata JSON，Agent 可动态扩展字段
37. **Agent 工作目录复用** — 保留上次执行的 git checkout，下次复用
38. **Thinking Level** — per-agent 推理深度配置 (low/medium/high/max)
39. **Webhook Delivery 审计** — 每次 webhook 触发完整记录 payload/状态/响应
40. **Agent 软删除** — archive 而非 delete，可恢复
41. **执行模式** — 定时任务两种模式: create_task (创建看板任务) vs run_only (直接执行)
42. **Usage 聚合** — 按小时/workspace/agent/model 聚合 Token 使用量
43. **插件仓库** — 集中管理所有插件：浏览/搜索/编辑/版本历史/Facet 可视化
44. **插件分享** — 将 Agent 自进化的私有插件分享给指定 Agent 或提升全局
45. **插件自动发布** — 进化质量达标后自动从 memory 发布为插件（prompt/tool/code/hook/service facet）
46. **信任等级** — Agent 审核链成本优化，连续通过自动升级，可跳过低风险审核
47. **链路追踪** — trace_id 全链路传播，webhook→chain→fanout→review 端到端可观测
48. **全局助手降级** — LLM 路由失败时自动切换为手动选择团队
49. **记忆仓库** — 集中管理所有 Agent 的记忆：浏览/搜索/验证/归档
50. **记忆分享** — 私有记忆可分享给指定 Agent 或全局化为团队知识
51. **记忆相关度注入** — 执行时按 FTS5 相关度检索记忆，而非全量灌入
52. **三层记忆模型** — Agent 私有 → 团队共享 → 跨团队全局，Brain 自动分类写入层级
52. **API Key 集中管理** — 三层继承(Agent→Workspace→User)、加密存储、月度预算、失效告警
53. **异步委托** — 全局助手委托后不阻塞，结果通过 IPC 事件异步回传
54. **Session 生命周期** — 按类型管理(chat/execution/chain/delegate)，自动压缩/归档/清理
55. **角色权限** — owner/admin/member 三级权限矩阵，覆盖全部操作
56. **并发冲突处理** — 乐观锁 + 用户操作优先规则，防止审核与手动操作冲突
57. **外部 Runtime 健康检查** — 定期/按需检查 CLI/服务可用性，不可用时快速失败
58. **统一插件系统** — Skills/MCP/工具/自进化全部统一为 Multi-Facet Plugin，原子化解耦
59. **MCP Bridge 兼容** — 现有 MCP 服务器通过 mcp-bridge 自动桥接为插件，三层继承不变

                                -- 可选: ['learning','skills','code','tools','search','memory']
  roles            TEXT          -- JSON: ['文案','数据分析'] （池认领模式：Agent 具备的角色标签）

**三级架构在数据模型中的体现：**
- 没有 `is_brain` 或 `level` 字段 — 每个 Agent 地位平等，层级由 `superior_id` 链决定
- `superior_id = NULL` → 顶层负责人（1号 Agent）或全局助手
- `superior_id = 某Agent` → 该 Agent 的直属下级，输出由上级审核
- `l2_capabilities` → 每个 Agent 内置的 L2 能力（Brain/Learning/Skills/Code 全部内化）
- 审核规则：直属上级审核直属下级，只审一层

**全局助手规则：**
- 用户注册时自动创建一个 `agent_type='global'` 的全局助手
- `workspace_id = NULL`（不归属任何团队）
- 全局助手不可删除，但可修改配置/人设
- 全局助手有自己的记忆系统（跨所有团队的全局记忆 → global_memories 表）
- 全局助手与团队负责人是**委托关系**（不是上下级，不审核负责人）
- 全局助手的 L2 能力：`['learning','skills','tools','search','memory','delegate','team_manage']`
- 全局助手独有的内部工具：
    · `delegate_to_team(workspace_id, prompt)` — 委托任务给某团队
    · `promote_to_global(memory_id)` — 将 workspace 记忆提升为全局记忆
    · `create_workspace(...)` — 创建新团队（AI 建团队入口）
    · `cross_team_summary(workspace_ids)` — 跨团队汇总
    · `manage_agent(action, agent_id, ...)` — 管理 Agent（跨团队）
    · `search_all_workspaces(query)` — 全局搜索

**顶层 Agent（1号负责人）规则：**
- 创建 workspace 时自动创建一个 `superior_id = NULL, agent_type='team'` 的 Agent 作为团队负责人
- 负责人不可删除，但可修改配置
- 负责人的输出直达用户（无上级审核）
- 负责人审核其直属下级的输出
- 负责人拥有完整 L2 能力：`['learning','skills','code','tools','search','memory','decompose','review']`
- 用户跟负责人对话 = 团队内入口（但全局助手是更自然的默认入口）

**全局助手 vs 负责人 对比：**

| 维度 | 全局助手 | 团队负责人 |
|------|----------|------------|
| 归属 | 用户级，无 workspace | 团队级，属于某 workspace |
| 数量 | 每用户 1 个 | 每团队 1 个 |
| 能力 | 路由/委托/建团队/跨团队 | 拆解/指派/审核/汇总 |
| 审核 | 不审核任何人 | 审核直属下级 |
| 业务深度 | 浅（路由层） | 深（懂团队业务） |
| 输出 | 直达用户 | 直达用户 |
| 记忆 | 全局记忆（跨团队） | 团队记忆（团队内） |

## 六、核心机制

### 6.1 任务流转完整设计

#### 谁能创建任务

| 创建者 | 场景 | 审核要求 |
|--------|------|----------|
| 用户 | 看板手动创建 | 免创建审核，直接入库 |
| 负责人 | 拆解用户需求 | 免审核（负责人是顶层，输出直达用户） |
| Agent | 执行中发现需子任务 → 调用 `task_create` 工具 | 该子任务创建行为本身属于 Agent 输出的一部分，随主结果一并提交上级审核 |

#### 谁能指派任务

**核心规则：只能向下指派，不能跨级、不能向上、不能平级。**

```
指派权限矩阵:
  用户   → 可指派给任何 Agent（用户是最高权限）
  负责人 → 可指派给任何直属下级
  中层   → 可指派给自己的直属下级
  Agent  → 不能直接指派（Agent 需通过 task_create 工具创建子任务，
           子任务自动归属于该 Agent 的下级）
```

**指派流程：**

```
场景 1: 用户在看板创建任务，指派给 Agent X
  → task 创建 (column='待办', assignee=Agent X)
  → 自动入 job_queue (type='task_assign')
  → 调度器 claim → Agent X 执行
  → 结果 → 上级审核
  → 通过 → task 移到 '已完成'

场景 2: 用户对话负责人，负责人拆解指派
  → 用户发消息 → 负责人理解意图
  → 负责人创建父任务 (assignee=负责人自己, column='进行中')
  → 负责人创建子任务 (assignee=各下级 Agent, column='待办')
  → 子任务入 job_queue → Agent 们执行
  → 子结果逐个回负责人审核
  → 全部子任务通过 → 负责人汇总 → 父任务完成 → 回复用户

场景 3: Agent 执行中创建子任务
  → Agent A 正在执行任务，发现需要 Agent B 协助
  → Agent A 调用 task_create(title, assignee=Agent B)
  → ⚠️ 子任务不立即生效！随 Agent A 的执行结果一起提交上级审核
  → 上级审核 Agent A 的输出（含子任务创建请求）
  → 审核通过 → 子任务正式创建 + 入队 → Agent B 执行
  → 审核退回 → 子任务不创建，Agent A 重做

场景 4: 按角色池认领（可选模式）
  → 上级创建任务时不指定具体 Agent，只指定角色/标签
  → task 创建 (assignee_type='role', assignee_id='文案', column='待办')
  → 入 job_queue (type='pool_claim')
  → 调度器匹配: 查找 role='文案' 且 status='idle' 的 Agent 列表
  → 认领策略（三选一，在任务或团队配置中指定）:
      · 'load_balance' — 选当前队列最短的 Agent（默认）
      · 'round_robin' — 轮流分配
      · 'first_idle' — 谁先空闲谁拿
  → 调度器代为 claim → 写入实际 agent_id → 正常执行
  → 结果仍由该 Agent 的直属上级审核（审核链不变）
```

#### 池认领模式补充说明

```
适用场景:
  · 同一角色有多个 Agent（3 个文案 Agent 都能写小红书）
  · 上级不关心"谁来做"，只关心"这类人来做"
  · 需要负载均衡（避免某个 Agent 积压太多）

不适用场景:
  · 任务需要特定 Agent 的上下文/记忆（必须指定）
  · 任务有保密性要求（只能特定人看）
  · 上级明确知道谁最合适

数据模型变更:
  tasks 表:
    assignee_type  TEXT  -- 'agent'|'user'|'role'  (新增 'role')
    assignee_id    TEXT  -- agent_id / user_id / role 标识
    claim_strategy TEXT  -- 'load_balance'|'round_robin'|'first_idle' (仅 role 模式)
    claimed_by     TEXT  → agents.id  -- 实际认领的 Agent（role 模式时回填）

  agents 表:
    roles          TEXT  -- JSON: ['文案', '数据分析', '策略'] （Agent 具备的角色标签）

  job_queue 表:
    job_type 新增值: 'pool_claim'

调度器逻辑扩展:
  轮询时发现 job_type='pool_claim':
    1. 读取 assignee_id（角色标识）
    2. 查找 agents WHERE roles LIKE '%"角色"%' AND status='idle'
    3. 按 claim_strategy 选择一个 Agent
    4. 回填 task.claimed_by = 选中的 agent_id
    5. 更新 job_queue.agent_id = 选中的 agent_id
    6. 正常执行流程

  无可用 Agent 时:
    · 任务留在队列中等待
    · 超过阈值（如 10 分钟无人认领）→ 通知上级
    · 上级可手动指派或扩容 Agent

与审核链的关系:
  · 认领后 → 该 Agent 的直属上级审核（不变）
  · 如果同角色的多个 Agent 上级不同 → 谁认领谁的上级审
  · 退回重做 → 仍由同一 Agent 重做（不会换人，除非上级 reassign）
```

#### 任务状态流转（自动 + 手动）

```
┌─────────────────────────────────────────────────────────────┐
│                    任务状态机                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  创建 ─→ 待办 ─→ 进行中 ─→ 审核中 ─→ 已完成                  │
│            │        ↑         │         │                   │
│            │        │         ↓         ↓                   │
│            │        └──── 退回重做      已归档                │
│            │                                                │
│            └───→ 已阻塞 ───→ 进行中（解除阻塞）               │
│                                                             │
└─────────────────────────────────────────────────────────────┘

自动流转规则（执行引擎驱动）:
  待办 → 进行中     : job_queue 被 claim 时自动触发
  进行中 → 审核中   : Agent execution 完成时自动触发
  审核中 → 已完成   : 上级审核通过时自动触发
  审核中 → 进行中   : 上级退回时自动触发（重新执行）

手动流转（用户在看板拖拽）:
  用户可以手动把任务拖到任何列
  手动拖到「已完成」= 用户手动标记完成（跳过审核）
  手动拖到「进行中」= 重新触发执行
  手动拖到「待办」= 暂停（从队列中移除）
  手动拖到「已阻塞」= 挂起，不再调度
```

#### 审核机制（上级审下级）

```
审核触发: Agent execution phase 进入 'reviewing'
  → 系统查找该 Agent 的 superior_id
  → 若 superior_id = NULL（顶层负责人）→ 无需审核，直达用户
  → 若 superior_id 存在 → 调用上级 Agent 的 Brain 进行审核
  → 传入:
      · 下级 Agent 完整输出内容
      · 所有工具调用 + 结果
      · 原始任务描述
      · 下级 Agent 中间思考过程（如有）
      · 该 Agent 历史表现（成功率、常见问题）
  → 上级 Agent 返回审核决定 + 附带动作

硬规则: 直属上级全量审核直属下级输出，无例外。
  · 每次审核都是上级 Agent 的一次 LLM 调用
  · 只审一层（不层层审到顶）
  · 顶层负责人的输出直达用户（用户是唯一"审核者"）
  · 用户直接跟某 Agent 对话时，结果仍由该 Agent 的上级审核
```

#### 上级审核可执行的动作

```
上级审核时不只是"通过/打回"，而是一个完整的管理决策点:

┌─────────────────────────────────────────────────────────────────┐
│ 动作            │ 说明                     │ 后续流转            │
├─────────────────┼──────────────────────────┼────────────────────┤
│ ✅ 通过         │ 结果合格，直接生效        │ 写入评论 → 任务完成 │
│ ✏️ 修改后通过   │ 上级微调内容再通过        │ 修改版写入 → 完成   │
│ 🔄 打回重做     │ 附带指导/纠偏/建议        │ Agent 收到意见重做  │
│ 👉 转派他人     │ 换一个 Agent 来做         │ 任务 reassign → 新人执行 │
│ 📝 补充后继续   │ 上级补充信息/约束条件      │ Agent 在原基础上继续 │
│ ⏸️ 挂起         │ 暂不处理，改日再审        │ 任务移到「已阻塞」  │
│ 🔀 变更+流转    │ 改优先级/截止日/标签等     │ 按新条件重新流转    │
└─────────────────┴──────────────────────────┴────────────────────┘
```

**各动作详细说明:**

```
1. 通过 (approve)
   → 输出写入 task_comments（作为执行结果）
   → task 标记「已完成」
   → 通知用户/相关方

2. 修改后通过 (modify)
   → 上级编辑/润色输出内容
   → 修改后的版本写入 task_comments（标注"经上级修改"）
   → task 标记「已完成」

3. 打回重做 (reject)
   → 上级写明: 哪里不对 + 怎么改 + 具体建议
   → 指导意见作为新的 context 传给下级 Agent
   → Agent 重新执行（附带上级反馈 + 原始输出 + 修改方向）
   → 重做计数 +1，超过 max_retries → 标记失败，上级决定下一步
   → 重做结果再次提交上级审核（循环直到通过或放弃）

4. 转派他人 (reassign)
   → 上级认为这个 Agent 不适合做这个任务
   → 选择另一个下级 Agent 来接手
   → 附带转派原因（让新 Agent 知道为什么换人）
   → 原 Agent 的执行标记 cancelled
   → 新 Agent 收到任务 + 原 Agent 的输出（作为参考）+ 上级指导
   → 新 Agent 执行 → 结果再提交上级审核

5. 补充后继续 (supplement)
   → 上级觉得方向对，但缺信息/约束不够
   → 上级补充: 额外要求、参考资料、约束条件
   → Agent 在原输出基础上继续完善（不是从头来）
   → 补充后的结果再提交审核

6. 挂起 (suspend)
   → 上级现在不想处理（等其他依赖、等用户确认等）
   → 任务移到「已阻塞」列
   → 上级可以随时恢复 → 继续审核流程

7. 变更+流转 (change_and_route)
   → 上级修改任务本身的属性:
     · 提升/降低优先级
     · 修改截止日期
     · 添加/移除标签
     · 修改任务描述（追加需求）
     · 改变所在列（手动状态变更）
   → 修改完成后选择下一步: 打回重做 / 转派 / 继续等待
```

#### 审核附带信息结构

```typescript
interface ReviewDecision {
  action: 'approve' | 'modify' | 'reject' | 'reassign' | 'supplement' | 'suspend' | 'change_and_route';
  
  // 通用
  note?: string;                   // 上级批注（所有动作都可附带）
  
  // action = 'modify'
  modified_content?: string;       // 修改后的输出内容
  
  // action = 'reject'
  guidance?: string;               // 具体指导：哪里不对、怎么改
  suggestions?: string[];          // 具体建议列表
  
  // action = 'reassign'
  reassign_to_agent_id?: string;   // 转派目标 Agent
  reassign_reason?: string;        // 转派原因
  include_original_output?: boolean; // 是否把原输出给新人参考
  
  // action = 'supplement'
  supplement_info?: string;        // 补充的信息/约束
  
  // action = 'change_and_route'
  task_changes?: {
    priority?: string;             // 新优先级
    due_date?: number;             // 新截止日
    column_id?: string;            // 移到哪列
    labels_add?: string[];         // 添加标签
    labels_remove?: string[];      // 移除标签
    description_append?: string;   // 追加描述
  };
  next_action?: 'reject' | 'reassign' | 'suspend';  // 变更后的下一步
}
```

#### 审核结果在数据模型中的记录

```sql
-- agent_executions 表扩展
  review_status    TEXT  -- 'pending'|'approved'|'modified'|'rejected'|'reassigned'|'supplemented'|'suspended'|'review_failed'
  reviewed_by      TEXT  → agents.id
  review_note      TEXT  -- 上级批注
  review_guidance  TEXT  -- JSON: {guidance, suggestions} (reject 时)
  review_action_data TEXT -- JSON: 完整 ReviewDecision（用于审计追溯）
  review_retry_count INTEGER  -- 审核重试次数
  review_escalated_to TEXT    -- 升级到哪个上级
  redo_count    INTEGER       -- 被退回重做次数
  previous_execution_id TEXT  -- 关联上一次 execution（重做/补充链）
```

#### 重做与补充的执行记录模型

```
核心原则: 每次重做/补充 = 新建一条 execution 记录，通过 previous_execution_id 形成链。

reject（打回重做）:
  原 execution: status='completed', review_status='rejected'
  → 新建 execution:
      trigger_type = 'redo'
      previous_execution_id = 原 execution.id
      input_prompt = 原始任务 + 上级 guidance + 上次输出（作为反面参考）
  → 新 execution 完成后再提交上级审核
  → task 上的 redo_count++ (通过聚合 task_id 的 execution 链计算)
  → 超过 max_retries → 任务标记失败，通知上级

supplement（补充后继续）:
  原 execution: status='completed', review_status='supplemented'
  → 新建 execution:
      trigger_type = 'supplement'
      previous_execution_id = 原 execution.id
      input_prompt = 原始任务 + 原输出 + 上级补充信息
      （Agent 在原输出基础上继续完善，不是从头来）
  → 会话模式: 复用原 execution 的 session（session_mode='reuse'）
  → 补充后的结果再提交审核

reassign（转派）:
  原 execution: status='cancelled', review_status='reassigned'
  → 新建 execution（新 Agent）:
      trigger_type = 'reassign'
      previous_execution_id = 原 execution.id
      input_prompt = 任务描述 + 转派原因 + 原输出（若 include_original_output=true）

change_and_route（变更+流转）:
  · review_status 不设独立值，最终跟随 next_action:
    next_action='reject' → review_status='rejected'（执行重做流程）
    next_action='reassign' → review_status='reassigned'（执行转派流程）
    next_action='suspend' → review_status='suspended'（挂起）
  · task_changes 先应用到 task 表（修改优先级/截止日等），再执行 next_action

执行链查询:
  给定一个 task_id，可通过 previous_execution_id 链追溯完整执行历史:
  execution_1 (initial) → execution_2 (redo) → execution_3 (redo) → execution_4 (approved)
```

#### 审核流转示例

```
示例 1: 打回重做 + 指导
  文案 Agent 写了一篇小红书文案 → 提交运营总监审核
  运营总监: "标题太平了，要有冲突感。参考竞品 XXX 的写法，加入数字对比"
  → reject + guidance
  → 文案 Agent 重新写（带着上级指导 + 上次输出作为反面参考）
  → 再次提交 → 运营总监: "好多了" → approve

示例 2: 转派他人
  数据 Agent 被分配"写分析报告"但它更擅长数据采集不擅长写报告
  → 运营总监审核数据 Agent 的输出: "数据部分很好，但报告格式不行"
  → reassign 给 文案 Agent，附带: "用数据 Agent 的原始数据，重新组织成报告格式"
  → 文案 Agent 拿到数据 Agent 的输出 + 上级指导 → 写出最终报告

示例 3: 补充后继续
  策略 Agent 分析了本周数据，输出了初步结论
  → 运营总监: "分析得不错，但漏了抖音渠道的数据，补充进去"
  → supplement，附带抖音数据来源信息
  → 策略 Agent 在原输出基础上追加抖音分析 → 再次提交

示例 4: 变更+流转
  某任务原来是低优先级，上级审核时发现很紧急
  → change_and_route: priority='urgent', due_date=明天
  → next_action='reject', guidance="紧急！明天要用，今晚改好"
  → Agent 按新优先级重做
```

#### 父子任务

```
父任务: 上级拆解后自动创建
  · assignee = 上级自己（负责汇总）
  · column = '进行中'
  · 不入 job_queue（上级不需要被调度执行父任务）

子任务: 上级为每个下级创建
  · parent_task_id = 父任务 ID
  · assignee = 具体下级 Agent
  · 入 job_queue

完成条件:
  · 所有子任务 '已完成' → 父任务自动进入 '审核中'
  · 上级汇总子任务结果 → 生成最终交付
  · 父任务标记 '已完成'
  · 若子任务有失败/超时 → 父任务标记 'partial'，上级决定下一步

汇总触发机制（中层/负责人如何自动汇总）:
  · 监听事件: 每当子任务标记 '已完成'，检查同父任务下所有子任务状态
  · 触发条件: 所有子任务均为 '已完成' → 自动创建汇总任务入 job_queue
  · 汇总任务: type='aggregation', agent_id=父任务 assignee, payload={子任务输出列表}
  · 执行: 父任务 owner（中层）拿到所有子结果 → LLM 汇总 → 输出完整交付
  · 审核: 中层的汇总输出 → 提交其直属上级审核（层层向上）
  · 顶层负责人汇总后 → 直达用户（无外部审核）
  · partial 场景: 部分子任务失败 → 不触发自动汇总 → 通知上级手动决策

前端展示:
  · 父任务卡片上显示子任务进度条 (3/5 完成)
  · 展开父任务 → 看到子任务列表 + 各自状态
  · 子任务不单独占看板卡片位（折叠在父任务下）
```

#### 并发场景

```
同一 Agent 多个任务:
  · Agent 同一时间只执行一个任务（会话锁）
  · 队列中按 priority DESC, created_at ASC 排序
  · 高优先级任务可以排到前面

上级并发审核:
  · 上级 Agent 可以同时审核多个下级的输出（审核是独立 LLM 调用）
  · 审核不受上级 Agent 自身会话锁影响（审核 ≠ 执行任务）
  · 上级正在执行自己的任务时，仍可被触发审核下级

死锁预防:
  · Agent A 创建子任务给 Agent B
  · Agent B 正忙 → 子任务排队，Agent A 的主任务在 'reviewing' 等上级
  · 上级审核 Agent A → 通过 → 子任务入队 → 不依赖 Agent A
  · 禁止循环指派：不能 A→B→A（上下级链保证无环）
```

#### 审核的执行模型

```
审核 ≠ 任务执行，是一种独立的轻量 LLM 调用:

  1. 不走 job_queue — 不入队、不排队、不受调度器管控
  2. 不占用上级的会话锁 — 上级正在执行自己的任务时仍可审核
  3. 无共享上下文 — 每次审核是独立的 LLM 请求（独立 system prompt + 被审内容）
  4. 可并发 — 上级可同时审核多个下级的输出（并行 LLM 调用）
  5. Token 计费归属 — 审核消耗的 Token 记在上级 Agent 的 execution 上
     （创建 trigger_type='review' 的 execution 记录，关联被审的 execution_id）

  执行流程:
    下级 execution 完成 (phase='reviewing')
      → 直接调用上级 Agent 的 Brain（不经过 job_queue）
      → 构造审核 prompt: system_prompt + 被审内容 + 上下文
      → 单次 LLM 调用 → 解析为 ReviewDecision
      → 写入审核结果 → 触发后续流转

  与任务执行的区别:
    | 维度 | 任务执行 | 审核 |
    |------|----------|------|
    | 入队 | 走 job_queue | 直接调用 |
    | 会话锁 | 占用 | 不占用 |
    | 并发 | 1（串行） | 无限制 |
    | 工具调用 | 可用 | 不可用（纯判断） |
    | 超时 | stall_threshold | 30s 固定超时 |
    | 记录 | trigger_type='task_assign'等 | trigger_type='review' |
```

#### 故障降级（上级审核失败时）

```
上级 Agent 审核可能失败的场景:
  · LLM API 超时 / 网络错误
  · API Key 额度耗尽
  · Provider 全局宕机（如 OpenAI/Anthropic 故障）
  · 上级 Agent 配置错误导致持续失败

降级策略（逐级升级）:

  第 1 步: 重试（自动）
    → 审核调用失败 → 指数退避重试 3 次（5s, 15s, 45s）
    → 3 次均失败 → 进入第 2 步

  第 2 步: 向上升级
    → 查找上级的上级（superior_id 链上溯）
    → 让更高层级的 Agent 代为审核
    → 如果高层也失败 → 继续上溯
    → 到顶层负责人还是失败 → 进入第 3 步

  第 3 步: 通知用户，人工介入
    → 发送通知: "Agent X 的执行结果等待审核，但审核链不可用"
    → 任务标记 review_status = 'review_failed'
    → 用户可手动操作:
        · 手动通过（用户有最高权限）
        · 手动打回
        · 修复 Agent 配置后重试审核
        · 转派给其他 Agent

  超时兜底:
    · 审核停留在 'pending' 超过 30 分钟 → 自动触发第 2 步
    · 超过 2 小时无人处理 → 发送紧急通知
    · 不会自动通过（绝不跳过审核）

状态机扩展:
  reviewing → review_failed (审核链不可用)
  review_failed → reviewing (修复后重试)
  review_failed → completed (用户手动通过)
```

```
数据模型支持:
  agent_executions.review_status 新增值: 'review_failed'
  agent_executions.review_retry_count INTEGER DEFAULT 0
  agent_executions.review_escalated_to TEXT  -- 升级到哪个上级 Agent

  notifications.type 新增值: 'review_chain_failed'
```

#### 审核成本优化（信任等级 + Auto-Approve）

```
全量审核 = LLM 调用翻倍。一个 10 人团队每天 50 次执行 = 50 次额外审核调用。
引入信任等级机制，让表现稳定的 Agent 可跳过审核:

  Agent 信任等级 (trust_level):
    · 'probation' (试用期) — 新 Agent 默认，必须全量审核
    · 'standard' (标准) — 正常审核流程
    · 'trusted' (可信) — 低风险任务可跳过审核
    · 'autonomous' (自治) — 几乎所有任务跳过审核（仅保留高风险审核）

  自动升降级规则:
    · probation → standard: 连续 10 次审核通过（无退回）
    · standard → trusted: 连续 30 次审核通过 + 无一次 reject
    · trusted → autonomous: 需上级手动授权（不自动升级，太危险）
    · 任何级别 → 降一级: 被 reject 1 次立即降级
    · 任何级别 → probation: 连续 3 次 reject

  Auto-Approve 规则（trust_level='trusted' 或更高时）:
    · 低风险任务: 无工具调用、输出 < 2000 tokens → auto-approve
    · 中风险任务: 有工具调用但无副作用（只读操作）→ auto-approve
    · 高风险任务: 有写入操作、创建子任务、费用 > 阈值 → 仍需审核
    · 配置粒度: per-agent 可覆盖（某些 Agent 始终全量审核）

  成本节省估算:
    · 稳定团队（大部分 Agent 为 trusted）: 审核调用减少 60-70%
    · 新团队（全部 probation/standard）: 无优化，确保质量
    · 混合团队: 核心 Agent trusted + 新 Agent probation = 减少 40-50%

  数据模型:
    agents.trust_level TEXT NOT NULL DEFAULT 'probation'
    agents.consecutive_approvals INTEGER NOT NULL DEFAULT 0  -- 连续通过计数
    agents.total_rejections INTEGER NOT NULL DEFAULT 0       -- 总退回次数

  上级可手动调整:
    · 上级 Agent 或用户可手动设置下级的 trust_level
    · 手动设置不受自动规则约束
    · 日志记录: 谁在什么时候调整了谁的信任等级

  安全兜底:
    · autonomous 级别仍保留随机抽检（5% 概率仍走审核）
    · 用户可全局关闭 auto-approve（回退到全量审核模式）
    · workspace 设置: review_mode = 'strict' | 'trust_based' (默认 trust_based)
```

### 6.2 指令流向汇总

```
路径 0: 用户 → 全局助手 → 委托团队（默认路径，最自然）
  用户跟全局助手对话: "帮我写一篇小红书"
  → 全局助手 Brain 分析意图 → 识别目标团队
  → 全局助手调用 delegate_to_team(workspace_id, prompt)
  → 等效于在目标团队负责人会话中发起对话
  → 负责人接手 → 团队内正常拆解/指派/审核
  → 结果回传全局助手 → 全局助手组织语言呈现给用户

  全局助手自处理场景（不委托）:
    · 跨团队问题: "这周各团队进展" → 聚合数据直接回答
    · 通用问题: "帮我翻译这段话" → 自己处理
    · 团队管理: "把 Agent X 删了" → 执行管理操作
    · 建团队: "帮我建个开发团队" → 进入 AI 建团队流程

路径 1: 用户 → 负责人对话 → 任务拆解（进入团队后直接跟负责人聊）
  用户跟 1 号负责人对话
  → 负责人分析意图 + 拆解任务
  → 创建父任务 (负责人持有) + 子任务 (assignee = 下级 agents)
  → 子任务入 job_queue (type='task_assign')
  → 调度器 claim → 下级 Agent 执行
  → Agent 内部 Brain 自审 → 提交上级（负责人）审核
  → 负责人审核 → 通过/修改/退回
  → 全部子任务通过 → 负责人汇总 → 回复用户

路径 2: 用户 → 直接跟某 Agent 对话
  用户打开 Agent X 的对话窗口
  → Agent X 执行（内部 Brain 自审）
  → Agent X 提交给直属上级审核
  → 上级通过 → 结果返回用户
  → 上级退回 → Agent X 重做（用户可能等待稍久）

  前端展示策略（审核期间）:
    · Agent X 输出完成后立即展示给用户，标注"⏳ 待审核"
    · 审核通过 → 标注变为"✅ 已审核"
    · 审核修改后通过 → 替换为修改版内容，标注"✏️ 上级修改"
    · 审核退回 → 原内容标灰 + 提示"🔄 上级退回，正在重做..."
    · 用户无需等审核完才看到内容，但需知道内容可能被上级修改
    · 对话不自动产生看板任务（纯对话 ≠ 任务）

  对话 vs 任务的边界:
    · 纯对话（路径 2）: 只产生 execution 记录，不产生 task
    · Agent 主动调用 task_create 工具: 产生 task（需上级审核才生效）
    · 用户手动创建: 产生 task（路径 3）
    · 负责人拆解: 产生父+子 task（路径 1）
    · 看板上只展示显式创建的 task，不被对话产生的 execution 污染

路径 3: 用户 → 看板手动指派
  用户在看板创建任务，指定 Agent X
  → task 入库 (column='待办')
  → 入 job_queue (type='task_assign')
  → Agent X 执行 → 上级审核
  → 通过 → task 自动移到 '已完成'

路径 4: 定时触发 + 链式
  cron_job 触发 → 入 job_queue (type='cron')
  → Agent 执行 → 上级审核
  → 通过 → 检查 chain_config → 链式继续

路径 5: 中间管理者汇总
  负责人把"做一篇小红书"给中层 Agent（运营总监）
  → 运营总监拆解 → 分配给文案 Agent + 图片 Agent
  → 文案/图片各自完成 → 提交运营总监审核
  → 运营总监汇总 → 提交负责人审核
  → 负责人通过 → 返回用户
```

#### SQLite 并发写入策略

```
SQLite WAL 模式下写锁全局互斥。本系统高频写入场景:
  · job_queue claim（每 2s 轮询 + 状态更新）
  · agent_executions 创建/更新（审核完写结果）
  · checkpoint 写入（执行中定期保存）
  · usage_hourly 聚合更新

防 SQLITE_BUSY 策略:

  1. busy_timeout = 5000ms（所有连接统一设置）
     → 大多数写争用在 5s 内自然解除

  2. 写操作分级:
     · 关键写（claim/status）: BEGIN IMMEDIATE + 单行 UPDATE，持锁时间 <1ms
     · 批量写（聚合/清理）: 放在低峰时段（凌晨），或拆分为小事务
     · checkpoint 写: debounce 5s（不是每个 tool call 都写，攒一批再写）

  3. 连接池策略:
     · 读连接: 可多个（WAL 允许并发读）
     · 写连接: 全局唯一（单写者模式，内部排队）
     · 避免长事务（任何事务不超过 100ms）

  4. 硬性约束:
     · 单进程部署，不支持多实例水平扩展
     · 同一时刻最多 1 个 claim 操作在执行
     · journal_mode=WAL + synchronous=NORMAL（平衡性能与安全）

  5. 监控指标:
     · busy_wait_ms_p99 — 写等待时间 99 分位
     · write_queue_depth — 写操作排队深度
     · db_size_mb — 数据库文件大小
```

### 6.6 Runtime Driver 架构（Agent 执行运行时）

```
设计原则:
  · 平台只关心: 给任务 → 收流式事件 → 得最终结果 → 能取消
  · 外部 Runtime 全权执行，平台不拦截中间步骤，只审核最终输出
  · 内置 Runtime 支持细粒度工具拦截（per-tool-call 审核）
  · 每种 Runtime 是一个 Driver，实现统一接口

架构:
  ┌──────────────────────────────────────────────────────┐
  │         Execution Engine (调度/审核/追踪/生命周期)       │
  └────────────────────────────┬─────────────────────────┘
                               │ AgentRuntime 接口
           ┌───────────────────┼───────────────────┐
           ▼                   ▼                   ▼
     ┌──────────┐       ┌──────────┐       ┌──────────┐
     │ built-in │       │ claude-  │       │ opencode │  ...Hermes / custom
     │ runtime  │       │ code     │       │ driver   │
     │          │       │ driver   │       │          │
     └──────────┘       └──────────┘       └──────────┘
       直接调LLM           spawn子进程        spawn子进程
       工具可拦截           全权执行           全权执行
```

#### 核心接口

```typescript
interface AgentRuntime {
  readonly name: string;

  // 能力声明 — 平台据此决定审核策略
  getCapabilities(): RuntimeCapabilities;

  // 执行任务 — 返回流式事件
  execute(task: ExecutionTask): AsyncGenerator<AgentEvent>;

  // 取消执行
  cancel(executionId: string): Promise<void>;

  // 健康检查（外部 Runtime 进程是否可用）
  healthCheck(): Promise<{ ok: boolean; error?: string }>;
}

interface RuntimeCapabilities {
  // 平台能否拦截单个 tool_call（仅 built-in 为 true）
  toolInterception: boolean;
  // 是否支持流式输出（false = 只有最终结果）
  streaming: boolean;
  // 是否支持文件系统访问
  fileAccess: boolean;
  // 是否支持多轮对话（session 保持）
  multiTurn: boolean;
  // 是否支持恢复执行（checkpoint/resume）
  resumable: boolean;
  // 最大上下文窗口（影响 prompt 裁剪策略）
  maxContextTokens?: number;
}

interface ExecutionTask {
  executionId: string;
  prompt: string;                    // 用户指令/任务描述
  systemPrompt: string;              // Agent 角色定义
  workspacePath: string;             // 工作目录绝对路径
  context?: string;                  // workspace.context + 注入的技能/记忆
  files?: string[];                  // 相关文件路径
  env?: Record<string, string>;      // 环境变量 (agent.custom_env)
  args?: string[];                   // CLI 参数 (agent.custom_args)
  timeout?: number;                  // 超时 ms
  thinkingLevel?: string;            // 推理深度
  sessionId?: string;                // 多轮对话时复用 session
}
```

#### 审核模型差异

```
                    built-in           外部 Runtime (CC/opencode/Hermes)
─────────────────────────────────────────────────────────────────────────
审核时机            每个 tool_call      仅最终输出
审核粒度            单步拦截            整体通过/退回
流式事件            全部事件类型         text_delta + 生命周期事件
工具可见性          平台可见每个调用     仅最终 summary 提及
退回重做            精确到某步操作       整体重做（传入 guidance）
信任等级生效        可跳过特定工具审核   可跳过整体审核
```

#### Driver 注册与选择

```typescript
// Driver 注册
const runtimeRegistry = new Map<string, AgentRuntime>();
runtimeRegistry.set('builtin', new BuiltinRuntime(llmClient, toolRegistry));
runtimeRegistry.set('claude_code', new ClaudeCodeDriver(config));
runtimeRegistry.set('opencode', new OpenCodeDriver(config));
runtimeRegistry.set('hermes', new HermesDriver(config));
runtimeRegistry.set('custom', new CustomHttpDriver(config));

// 选择: agent.provider → 对应的 Driver
function getRuntime(agent: Agent): AgentRuntime {
  const runtime = runtimeRegistry.get(agent.provider);
  if (!runtime) throw new Error(`Unknown provider: ${agent.provider}`);
  return runtime;
}
```

#### 各 Driver 实现概要

**BuiltinRuntime（内置）**:
```
  · 直接调用 LLM API（Claude/GPT/等）
  · 工具通过 platform toolRegistry 注册和执行
  · 支持 per-tool-call 审核拦截
  · 支持 checkpoint/resume
  · 全部 AgentEvent 类型均可发射
  · 适用: 简单任务、需要细粒度控制的 Agent
```

**ClaudeCodeDriver（Claude Code）**:
```
  · 通信方式: spawn 子进程 `claude` CLI 或 Agent SDK
  · 输入: prompt + system_prompt + 工作目录 + 允许的工具列表
  · 输出: 解析 stdout JSON stream → 转换为 AgentEvent
  · 全权执行: CC 内部自主决定调用什么工具、读写什么文件
  · 取消: 发送 SIGTERM → 等待 5s → SIGKILL
  · 特殊: 支持 --allowedTools 限制工具范围（安全边界）
  · 适用: 复杂编程任务、需要文件操作的 Agent
```

**OpenCodeDriver（opencode）**:
```
  · 通信方式: spawn 子进程 `opencode` CLI
  · 输入: prompt + 配置文件 (.opencode.json 指定 model/tools)
  · 输出: 解析 stdout → AgentEvent
  · 全权执行: opencode 自主操作
  · 取消: SIGTERM
  · 特殊: 需要预先生成 .opencode.json 配置
  · 适用: 偏好 opencode 工具链的用户
```

**HermesDriver（Hermes）**:
```
  · 通信方式: HTTP API 调用（Hermes 作为独立服务运行）
  · 输入: POST /execute {prompt, context, workspace}
  · 输出: SSE 流 → 转换为 AgentEvent
  · 全权执行: Hermes 内部路由和工具调用
  · 取消: POST /cancel/{execution_id}
  · 特殊: 需要配置 Hermes 服务地址和 API key
  · 适用: 已有 Hermes 部署的用户
```

**CustomHttpDriver（自定义）**:
```
  · 通信方式: 用户自定义 HTTP/WebSocket endpoint
  · 配置: agent.config.endpoint + agent.config.auth
  · 协议: 平台定义标准请求/响应格式（OpenAPI spec）
  · 输入: POST {endpoint}/execute {task: ExecutionTask}
  · 输出: SSE stream 或 WebSocket frames → AgentEvent
  · 取消: POST {endpoint}/cancel/{execution_id}
  · 适用: 用户自建 Agent 服务、对接私有系统
```

#### 执行生命周期（统一）

```
无论哪种 Driver，Execution Engine 的处理流程一致:

  1. 前置阶段:
     · 准入检查 (Admission Gate)
     · Prompt 组装与裁剪（将 plugins/memories/context 组装到 systemPrompt 中）
     · 获取 Runtime 实例

  2. 执行阶段:
     · 调用 runtime.execute(task)
     · 消费 AsyncGenerator<AgentEvent>
     · 实时推送事件到 Renderer（通过 IPC 前端展示）
     · 记录事件到 execution_events 表

  3. 审核阶段:
     · built-in: 每个 tool_pending 事件 → 触发审核（除非信任等级跳过）
     · 外部 Runtime: execution_completed 事件 → 触发最终审核
     · 审核通过 → 标记完成
     · 审核退回 → 带 guidance 重新执行（对外部 Runtime = 新一轮 execute）

  4. 结束阶段:
     · 更新 execution 状态
     · 记录 token 用量（外部 Runtime 从 AgentEvent.usage 取）
     · 触发后续链式任务（如有）
     · 触发记忆提取（fire-and-forget）
```

#### 安全边界

```
外部 Runtime 的安全通过以下机制保障:

  文件系统隔离:
    · 每个 Agent 只能访问自己的 workspacePath
    · 通过 OS 级别限制（chroot 或 Docker --read-only + volume mount）
    · shared/ 目录只读挂载给非 leader Agent

  环境变量过滤:
    · 只传递 agent.custom_env 中声明的变量
    · 平台敏感变量（DATABASE_PATH, API keys）不传递

  超时强制:
    · execution.timeout (默认 300s) 到达后 SIGKILL
    · 防止外部进程永不退出

  输出审核:
    · 最终输出必须经上级 Agent 审核（除 autonomous 信任等级）
    · 审核 LLM 可检测: 敏感信息泄露、不当操作、偏离任务

  资源限制（可选，Docker 环境下）:
    · --memory 512m
    · --cpus 1
    · --network none（禁止外网访问，除非配置允许）
```

### 6.10 会话锁与并发控制

```
同一 Agent 同一时间只能执行一个任务：
  → 执行前获取 agent_id 锁
  → 锁有 TTL（默认 5 分钟），防止死锁
  → 执行完成释放锁
  → 新任务到达时若已锁定 → 入队等待
  → 超时未释放 → 监督器强制释放 + 标记失败

队列并发限制:
  - 全局队列上限: 100 pending jobs
  - 每 Agent 队列: 10 pending jobs
  - 每 Agent 并发: 1（串行执行）
```

### 6.11 监督器（三级看门狗）

```
Tier-1 (每 10s)：本地执行存活检测
  → 执行超过 stall_threshold (60s) 无活动 → 标记 stalled → 强制失败

  "无活动"的精确定义:
    · 无任何 AgentEvent 输出（包括 text_delta、thinking_delta、tool_pending 等）
    · streaming 中的每个 delta 都会重置 stall 计时器
    · LLM 正在生成（有 streaming delta 到达）= 活跃，不算 stall
    · 等待 LLM 首 token（网络延迟）= 可能 stall，但阈值宽容:
        首 token 等待使用 first_token_timeout (30s)，与 stall_threshold 独立
    · 工具调用执行中 = 活跃（tool_running 事件重置计时器）
    · 仅当真正"挂死"（进程无响应、LLM 连接断开无异常）才触发 stall

Tier-2 (每 30s)：锁过期回收
  → 扫描过期锁 → 释放 + 重入队
  → 孤儿执行清理（worker 崩溃后遗留）

Tier-3 (每 60s)：全局健康检查
  → 死 worker 检测（心跳超时）→ 标记 offline
  → 积压告警（pending > 阈值）→ 发送通知
```

### 6.12 Fan-Out 广播执行

```
定时任务触发 → 获取目标 Agent 列表
  → 可选: 动态获取（执行命令获取列表）
  → 可选: 静态绑定（task_group_bindings）
  → 创建执行轮次 (cron_executions)
  → 分批入队 (batch_size 控制)
  → 并发限制 (max_concurrent 控制)
  → 可选: 随机打乱顺序 (shuffle)
  → 每个 Agent 完成后 → 结果提交上级审核
  → 跟踪每个 Agent 执行+审核状态
  → 全部审核通过 → 轮次标记完成 + 上级生成汇总报告

轮次状态流转:
  'running' → 所有 Agent 正在执行/审核中
  'completed' → 全部 Agent 审核通过
  'partial' → 触发条件:
      · 部分 Agent 执行失败（execution failed）
      · 部分 Agent 审核被退回且超过 max_retries
      · 部分 Agent 审核链故障（review_failed）
      · 任一 Agent 的审核结果为 suspended
  'failed' → 触发条件:
      · 全部 Agent 执行失败
      · 超过 50% 的 Agent 审核未通过
      · 轮次超时（所有 Agent 总执行时间超过阈值）

  partial 场景处理:
    · 已通过的 Agent 结果正常记录
    · 未通过的标记原因（failed/rejected/review_failed）
    · 上级收到通知: "轮次部分完成（8/10），2个失败"
    · 上级可选: 忽略失败生成汇总 / 手动重试失败项 / 整轮重做
    · 汇总报告中标注哪些是成功数据、哪些缺失
```

### 6.13 执行断点恢复（Session Resumption）

```
Agent 执行可能因以下原因中断:
  · 进程崩溃 / OOM
  · 网络断开（LLM API 连接丢失）
  · 用户手动取消后改主意想继续
  · 服务重启/升级

断点恢复机制:

  1. Checkpoint 自动保存
    → 每完成一次工具调用后保存 checkpoint
    → checkpoint 内容: messages 历史、最后输出、工具状态、已完成步骤
    → 存入 agent_executions.checkpoint (JSON)
    → 执行正常完成后清空 checkpoint（节省存储）

  2. 故障检测
    → 执行中断（进程崩溃/网络断开）
    → 监督器 Tier-2 检测到: status='running' 但心跳超时
    → 标记 status='resumable'（不是 failed，区别对待）

  3. 恢复策略（三选一，按场景自动决定）
    a. 'continue' — 从 checkpoint 续做
       · 适用: 已完成部分工具调用，剩余工作明确
       · 恢复: 加载 checkpoint.messages → 继续 LLM 对话
       · 条件: checkpoint 存在 + 中断原因是 transient
    b. 'retry_last' — 重试最后一步
       · 适用: 工具调用超时或失败导致中断
       · 恢复: 回退到最后一次成功的 checkpoint → 重试失败的工具调用
    c. 'restart' — 从头重做
       · 适用: checkpoint 不可用 或 已过期（超过 1h）
       · 回退: 创建新 execution (trigger_type='redo', previous_execution_id=原 id)

  4. 恢复触发
    → 自动恢复: transient 错误 + checkpoint 有效 → 自动尝试 continue
    → 手动恢复: 用户点击"继续执行" → API: POST /api/executions/:id/resume
    → 配置: agent.config.auto_resume = true/false (默认 true)

  5. 数据模型
    agent_executions:
      status 新增值: 'resumable'
      checkpoint TEXT  -- JSON: {messages, tool_state, last_output, step_index, saved_at}

    resume 时:
      · 不创建新 execution（是同一次执行的延续）
      · 累加 duration_ms、tokens
      · 保留原始 started_at，更新 completed_at
```

### 6.14 Webhook/事件触发

```
除 cron 定时外，支持外部事件触发 Agent 执行:

  触发类型:
    1. Webhook — 外部系统 HTTP POST 触发
    2. Platform Event — 平台内事件触发（如任务完成、文件变更）

  Webhook 触发:
    · 创建 cron_job 时 schedule_type='webhook'
    · 自动生成唯一 URL: POST /api/webhooks/:job_id/trigger
    · 请求需携带签名验证: HMAC-SHA256(body, webhook_secret)
    · payload 透传给 agent 作为 input 的一部分
    · 支持条件过滤: webhook_filter JSON 匹配 payload 字段

  Platform Event 触发:
    · schedule_type='event'
    · event_filter: {"event": "task.completed", "conditions": {"project_id": "xxx"}}
    · 平台 EventEmitter 发射事件时，匹配 event_filter 的 job 自动触发
    · 支持的内部事件:
        · task.completed / task.failed
        · file.changed (特定目录文件变更)
        · agent.execution.completed (某 Agent 完成执行)
        · review.decided (审核完成)
        · custom.* (用户自定义事件名)

  并发策略 (concurrency_policy):
    · 'queue' (默认): 新触发排队，等上一次执行完再开始
    · 'replace': 取消正在执行的，立即启动新的
    · 'forbid': 正在执行时拒绝新触发，返回 409 Conflict

  使用场景:
    · GitHub PR merged → webhook → 代码 Agent 自动 review
    · 竞品网站更新 → webhook → 数据 Agent 抓取分析
    · 子任务全部完成 → event → 负责人自动汇总（补充汇总触发机制）
    · 文件上传到 shared/ → event → 文档 Agent 自动整理
```

### 6.15 错误分类与智能重试

```
执行失败不是千篇一律，不同错误应有不同处理策略:

  错误分类 (error_type):
    · 'transient' — 临时性故障（网络抖动、API 限流、超时）
        → 策略: 指数退避重试 (5s, 15s, 45s)
        → 最大重试: 3 次
        → 典型: HTTP 429/502/503, ETIMEDOUT, ECONNRESET

    · 'permanent' — 永久性故障（API Key 无效、模型不存在、权限不足）
        → 策略: 不重试，立即标记失败
        → 通知上级/用户修复配置
        → 典型: HTTP 401/403/404, invalid_api_key

    · 'resource' — 资源耗尽（Token 额度、磁盘空间、内存不足）
        → 策略: 不重试，暂停该 Agent 后续任务
        → 通知用户充值/扩容
        → 典型: insufficient_quota, context_length_exceeded

    · 'timeout' — 执行超时（stall / 总时长超限）
        → 策略: 检查 checkpoint 是否可用
        → 有 checkpoint → 标记 'resumable'（可恢复）
        → 无 checkpoint → 重试 1 次（可能是偶发慢响应）

  自动分类逻辑:
    → Agent Provider 返回错误时自动映射
    → HTTP status code → error_type 映射表
    → LLM API 错误码 → error_type 映射
    → 未识别的错误 → 默认 'transient'（允许重试一次）

  重试上下文:
    → 重试时携带: 原始 prompt + "上次尝试因 XXX 失败，请继续"
    → transient 重试: 完全相同请求（幂等）
    → timeout 重试: 可能需要拆分任务（上下文过长）

  前端展示:
    · 不同 error_type 显示不同图标和提示语
    · transient: "网络波动，正在重试..." (用户不需要操作)
    · permanent: "配置错误，请检查 Agent 设置" (引导修复)
    · resource: "额度不足，请充值" (引导充值)
    · timeout: "执行超时，可选择恢复或重做" (用户选择)
```

### 6.17 Skill 注入机制

> **注意**: 本节描述基础注入框架。插件（prompt facet）数据源已统一到 `plugins` + `agent_plugin_bindings` 表，详细注入逻辑见 6.27 "插件注入逻辑"。

```
Agent 执行时自动将已习得技能注入 system prompt:

  注入时机: Agent 开始新执行前（构建 system prompt 阶段）

  注入流程:
    1. 查询 agent_memories WHERE agent_id=X AND type='skill'
    2. 按 importance DESC + access_count DESC 排序
    3. 取 Top N 条（默认 5，受 token 预算限制）
    4. 格式化为 skill block 追加到 system prompt 末尾
    5. 更新 access_count++ 和 last_accessed_at

  注入格式（system prompt 内）:
    ---
    ## 已习得技能（自动注入）

    ### 技能: {skill_name}
    {skill_content}

    ### 技能: {skill_name_2}
    {skill_content_2}
    ---

  Token 预算控制:
    · 技能注入总 token 不超过 context window 的 10%
    · 超出时按 importance 截断
    · 可在 agent.config 中配置: skill_injection_budget: 2000 (tokens)

  技能衰减:
    · 30 天未被访问的技能 importance -= 0.1（自然衰减）
    · importance 降到 0.1 以下 → 不再注入（但不删除）
    · 用户可手动 pin 某技能（importance 固定为 1.0，不衰减）

  与审核的关系:
    · 技能是 Agent 私有的，不受上级审核
    · 但技能产出的结果仍然需要上级审核
    · 上级退回时如果指出"技能有问题" → 可触发技能修正
```

### 6.18 任务依赖与自动阻塞

```
任务之间可以建立依赖关系（blocks/blocked_by）:

  依赖类型:
    · finish_to_start (默认): A 完成后 B 才能开始
    · start_to_start: A 开始后 B 才能开始

  自动阻塞/解除:
    · 创建依赖时: 如果 blocking_task 未完成 → blocked_task 自动进入 '已阻塞' 列
    · blocking_task 完成时: 检查其 blocked 列表
      → 所有 blocker 都已完成 → 自动解除阻塞 → 任务回到 '待办'
      → 仍有其他 blocker 未完成 → 保持阻塞

  防循环检测:
    · 添加依赖前检查是否会形成环 (DFS/BFS)
    · A blocks B, B blocks C → 不允许 C blocks A

  前端展示:
    · 任务卡片上显示 "🔗 被 3 个任务阻塞" / "🔗 阻塞 2 个任务"
    · 点击展开依赖列表
    · Gantt 视图中用箭头连线表示依赖关系
    · 看板中被阻塞的任务卡片置灰 + 锁图标

  数据模型:
    task_dependencies 表（已在 5.4 定义）

  API:
    POST /api/tasks/:id/dependencies/add     -- {blocking_task_id, dependency_type}
    POST /api/tasks/:id/dependencies/remove  -- {dependency_id}
    GET  /api/tasks/:id/dependencies         -- 获取依赖列表 (blocks + blocked_by)
```

### 6.19 准入检查（Admission Gate）

```
触发任何自动执行前，先验证 Agent 是否具备执行条件:

  检查项:
    1. Agent 存在且未归档 (archived_at IS NULL)
    2. Agent 状态为 idle 或 busy 但队列未满
    3. Agent 配置有效（API Key 有效、model 非空）
    4. Agent 所属 workspace 未被暂停/删除

  检查时机:
    · cron_job 触发时（admission_gate=1 时生效）
    · webhook 到达时
    · event 触发时
    · pool_claim 匹配时

  检查结果:
    · 通过 → 正常入 job_queue
    · 失败 → cron_execution 标记 status='skipped' + failure_reason
    · 不消耗重试次数（skipped ≠ failed）
    · 不触发失败通知（减少噪音）

  与"失败"的区别:
    | 场景 | 分类 | 说明 |
    |------|------|------|
    | Agent offline | skipped | 暂时不可达，下次触发时可能恢复 |
    | Agent archived | skipped | 永久不可达，但不算执行失败 |
    | API Key 过期 | skipped | 配置问题，不应该入队然后报错 |
    | 执行中 LLM 报错 | failed | 真正的执行失败 |
    | 执行超时 | failed | 已消耗资源的失败 |

  优势:
    · 避免无意义的入队+失败循环（Agent 离线时不堆积失败记录）
    · 失败率统计更准确（skipped 不计入失败率）
    · 更快反馈（不需要等 claim→执行→失败 整个流程）
```

### 6.20 Autopilot 失败自动暂停

```
定时任务连续失败时自动暂停，防止"跑飞":

  监控周期: 每 24 小时扫描一次（监督器 Tier-3 层级）

  暂停条件（三个必须同时满足）:
    · 最近 7 天内累计 50+ 次运行
    · 失败率 ≥ 90%（不含 skipped）
    · 当前状态为 enabled（已暂停的不重复处理）

  暂停动作:
    1. cron_jobs.enabled = 0（停止后续触发）
    2. 创建通知: type='autopilot_paused', severity='warning'
    3. 通知接收者: cron_job 创建者 + workspace owner
    4. 通知内容: "定时任务「{name}」因连续失败已自动暂停（过去7天失败率92%）"

  恢复:
    · 用户手动恢复: POST /api/cron-jobs/:id/update {enabled: 1}
    · 恢复后重新计算 next_trigger_at
    · 恢复后计数器清零（重新开始统计）

  配置项（可在 workspace 设置中调整）:
    · lookback_days: 7 (回溯天数)
    · min_runs: 50 (最小样本量)
    · fail_threshold: 0.9 (失败率阈值)
    · monitor_interval_hours: 24 (扫描间隔)

  数据模型:
    cron_jobs 表新增:
      auto_paused_at INTEGER     -- 自动暂停时间（区分手动暂停）
      auto_pause_reason TEXT     -- 暂停原因 "failure_rate: 92% (46/50 in 7 days)"
```

### 6.21 任务订阅与通知偏好

  自动订阅（创建 subscriber 记录）:

### 6.23 重复任务检测（Duplicate Guard）

```
创建任务前检查是否已存在相同标题的活跃任务:

  检测逻辑:
    1. 标准化标题: lowercase + trim + 多空格合并为单空格
    2. 查询: 同 workspace + 同 project (if specified) + 标准化标题相同
    3. 排除已完成/已取消的任务 (status NOT IN 'done','cancelled','archived')
    4. 找到匹配 → 提示用户"已存在相似任务: {identifier}"

  防并发:
    · 使用 SQLite 事务隔离（IMMEDIATE 模式）
    · 查重 + 创建在同一事务内完成
    · 避免两个 Agent 同时创建相同任务

  可跳过:
    · API 参数 allow_duplicate=true 可绕过检测
    · 用户手动创建时前端先查询，展示提示但不阻止
    · Agent 通过 task_create 工具创建时强制检查

  检测范围:
    · 标题完全匹配（标准化后）
    · 不做模糊匹配（避免误判）
    · 仅限 active 任务（已完成的可以重新创建同名任务）
```

### 6.24 任务编号系统

```
每个 workspace 有独立的自增编号，格式: '{prefix}-{number}':

  编号生成:
    1. 首次创建任务时，从 workspace.name 生成 prefix:
       · 取 name 首字母大写（如 "开发团队" → "KF", "Content Team" → "CT"）
       · 或用户手动设置 workspace.issue_prefix
    2. 每次创建任务: workspace.issue_counter++ (原子操作)
    3. task.number = 新计数值
    4. task.identifier = '{prefix}-{number}' (如 "DEV-42")

  特性:
    · workspace 内唯一，跨 workspace 可重复
    · 递增，不回收（删除任务不释放编号）
    · 不可修改（创建后固定）
    · 可搜索: 全局搜索支持按 identifier 匹配

  用途:
    · 口头沟通: "看下 DEV-42 的进度"
    · 评论引用: 输入 #42 自动链接
    · URL 路径: /teams/:id/tasks/DEV-42 (slug 模式)
    · Agent 引用: Agent 在输出中引用 task identifier

  数据库:
    workspaces.issue_prefix TEXT
    workspaces.issue_counter INTEGER DEFAULT 0
    tasks.number INTEGER NOT NULL
    tasks.identifier TEXT NOT NULL
    UNIQUE(workspace_id, number)
```

### 6.25 Agent 工作目录复用

```
Agent 执行完成后保留工作目录状态，下次执行复用:

  场景:
    · 代码类 Agent: 首次执行 clone 代码库 → 后续执行复用 checkout
    · 文件类 Agent: 首次创建结构 → 后续在已有文件基础上工作
    · 省去重复的环境准备时间（clone/install/build）

  机制:
    1. 执行完成时: 保存 prior_work_dir 到 agents 表
       · 不保存临时状态（.tmp 文件清理）
       · 保存 git 状态（branch、staged files 等）
    2. 下次执行时: 检查 prior_work_dir 是否存在
       · 存在 → workingDir 设为该路径
       · 不存在 → 新建目录（首次执行或目录被清理）
    3. Session 复用: prior_session_id 与目录配合
       · session + workdir 一起传给 Agent Provider
       · Provider 可利用对话历史继续工作

  清理策略:
    · 磁盘空间不足时: 按 last_active_at ASC 清理最久未用的目录
    · Agent 归档时: 标记目录可清理（不立即删除）
    · 手动清理: 管理员可在设置中重置 Agent 工作目录

  安全约束:
    · Agent 只能访问自己的 prior_work_dir
    · 不能通过 workdir 复用访问其他 Agent 的文件
    · workspace 删除时联动清理所有 Agent 目录

  配置:
    · agent.config.reuse_workdir: true/false (默认 true)
    · 某些场景（如安全审计 Agent）需要每次干净环境

  数据模型:
    agents.prior_session_id TEXT -- 上次 session（Provider 用于恢复对话）
    agents.prior_work_dir TEXT   -- 上次工作目录路径
```

### 6.27 统一插件系统（Plugin System）

```

#### 生命周期状态

```
                    ┌─── failed
                    │
draft → validating ─┤
                    │
                    └─── pending_review / pending_user_confirm → enabled ⟷ disabled
                                                                    │
                                                              quarantined / rolled_back

状态说明:
  · draft          — 刚创建或进化产出，未验证
  · validating     — 静态分析 + 安全扫描中
  · pending_review — 需 Brain 审核（medium risk）
  · pending_user_confirm — 需用户确认（high risk / service facet）
  · enabled        — 生效中
  · disabled       — 用户手动禁用（保留数据）
  · quarantined    — 运行时异常超限，自动隔离
  · rolled_back    — 版本回滚到上一个稳定版
  · failed         — 验证未通过，不可启用

自进化快速路径（仅 prompt-only + low risk + confidence ≥ 0.7）:
  draft → validating → enabled（自动批准，无需人工介入）
```

#### 插件注入逻辑（按 Facet）

```
Agent 执行前，按 facet 类型分别组装:

═══ Prompt Facet 注入 ═══

  Step 1: 收集候选（三层合并）
    a. Agent 私有绑定的:
       SELECT p.* FROM plugins p
       JOIN agent_plugin_bindings b ON p.id = b.plugin_id
       WHERE b.agent_id = :agent_id AND b.enabled = 1 AND p.has_prompt = 1
    b. Workspace 全局的（未被禁用）:
       SELECT p.* FROM plugins p
       WHERE p.workspace_id = :wid AND p.scope = 'workspace' AND p.has_prompt = 1
       AND p.id NOT IN (SELECT plugin_id FROM agent_plugin_bindings WHERE agent_id = :aid AND enabled = 0)
    c. 全局的（未被禁用）:
       SELECT p.* FROM plugins p
       WHERE p.scope = 'global' AND p.user_id = :uid AND p.has_prompt = 1
       AND p.id NOT IN (SELECT plugin_id FROM agent_plugin_bindings WHERE agent_id = :aid AND enabled = 0)

  Step 2: 激活过滤
    · always=true 的始终包含
    · always=false 的: 当前任务标签 ∩ activationRules.taskTags 非空才包含

  Step 3: 排序
    · pinned 置顶
    · 其余按 prompt_priority DESC + use_count DESC
    · 同分: private > workspace > global

  Step 4: Token 裁剪
    · 预算: context window 的 10%
    · 按顺序逐个加入，超出截断

  Step 5: 注入格式
    ---
    ## 可用能力

    ### [🔌 private] {plugin_name}
    {prompt_content}

    ### [🏢 workspace] {plugin_name}
    {prompt_content}

    ### [🌍 global] {plugin_name}
    {prompt_content}
    ---

═══ Tool Facet 注入 ═══

  · 收集所有 enabled 且有 tool facet 的 plugin
  · 展平 tools 数组 → 合入 Agent 可用工具列表
  · 命名空间: {plugin_name}.{tool_name}（防冲突）
  · MCP bridge 类: 透传 MCP server 的工具定义

═══ Hook Facet 激活 ═══

  · 收集所有 enabled 且有 hook facet 的 plugin
  · 按 event 分组 → 按 priority ASC 排序
  · Agent 触发对应生命周期事件时依序执行
  · 返回 action: pass/flag/block/modify

═══ Service Facet 管理 ═══

  · Plugin enabled 时: 启动 service（按 schedule cron 调度或常驻）
  · Plugin disabled 时: 停止 service
  · 运行异常计数器: 连续 3 次异常 → quarantined

═══ 反馈更新 ═══

  · 使用后: use_count++, last_used_at 更新
  · 执行成功 → success_count++
  · 执行失败 → failure_count++
  · importance 动态调整: +0.05(成功) / -0.2(显式负反馈)
```

#### Scope 继承与合并

```
Agent 生效的插件集 = merge(global_plugins, workspace_plugins, private_plugins)

合并规则:
  · 默认 merge: 三层叠加，同名插件内层覆盖外层
  · 同名覆盖: private 版本 > workspace 版本 > global 版本
  · 单独禁用: agent_plugin_bindings.enabled = 0 可禁用任何层的插件

#### 自进化产出 Plugin

```
L2 Learning 检测到模式后，按类型路由到对应 facet:

  信号分类与路由:
    · 指令/方法论模式 → prompt facet
      (例: "每次写标题都用这个结构" → 提取为 prompt 插件)
    · 工具编排模式   → tool facet
      (例: "总是先搜索再总结" → 编排为可复用工具)
    · 数据转换模式   → code facet
      (例: "日期总是转成 YYYY-MM-DD" → 代码处理器)
    · 质量反馈模式   → hook facet
      (例: "每次回复前检查字数" → afterExecution 钩子)
    · 监控需求模式   → service facet
      (例: "每小时检查竞品价格" → 定时服务)

  产出流程:
    1. L2 识别模式 → 分类 facet 类型
    2. 生成 plugin manifest + 对应代码/内容
    3. 进入 validating 状态（静态分析）
    4. 风险评估:
       · prompt-only + low risk + confidence ≥ 0.7 → 自动启用
       · tool/code facet → Brain 审核 + 用户确认
       · hook/service facet → 必须用户确认
    5. 通过后 → enabled，绑定到源 Agent

  版本迭代:
    · 自进化可能产出"已有插件的改进版"
    · 相似度 > 0.8 → 合并为版本更新（version + 1）
    · 相似度 < 0.8 → 创建为新插件
    · 保留最近 5 个版本，支持回滚

  从 memory 到 plugin 的发布:
    · 自动发布: importance ≥ 0.6 AND access_count ≥ 3
    · 手动发布: 用户在记忆面板点击"发布为插件"
    · 发布时: 根据内容类型选择 facet，格式化为 manifest
    · 发布后: 源 memory 标记 published_plugin_id
```

#### 安全沙箱

```
所有非 prompt 的 facet（tool/code/hook/service）在沙箱中执行:

  隔离模型:
    · 每个 plugin 独立 Bun Worker
    · 内存上限: 128MB per worker
    · CPU 时间: tool/code/hook 30s 超时，service 无限（但受调度控制）
    · 文件系统: 只能访问 workspace 目录（如 permissions 声明）
    · 网络: 只能访问 permissions.network.allow 中的域名

  权限强制:
    · Manifest 声明 → 运行时代理强制执行
    · PluginContext.fetch() 拦截非法域名 → throw PermissionDenied
    · PluginContext.storage 执行 maxBytes 限制
    · PluginContext.secrets 只返回声明过的密钥

  静态分析（validating 阶段）:
    · 禁止: process.env 直接访问、require('child_process')、eval()
    · 禁止: import src/kernel/*（只能用 SDK）
    · 禁止: 直接 LLM API 调用（必须通过 ctx.invokePlugin）
    · 检查: 所有 import 必须在白名单内

  审批分级:
    · low risk (prompt-only, readonly tools): 自动审批
    · medium risk (network access, code execution): Brain 审核 + 用户确认
    · high risk (filesystem write, secrets, service): 必须用户确认

  运行时防护:
    · 异常计数器: 连续 3 次 throw → quarantined
    · 内存超限 → kill worker + quarantined
    · 超时 → kill worker + failure_count++
    · 死循环检测: 30s 无 IO → kill
```

#### Hook 系统（12 个钩子点位）

```
Agent 生命周期钩子:
  ┌─────────────────────────────────────────────────────────┐
  │ beforePromptAssembly → afterPromptAssembly              │
  │         ↓                                               │
  │ beforeExecution → [LLM Call] → afterExecution           │
  │         ↓                                               │
  │ onToolCall (每次工具调用触发)                             │
  │ onReviewSubmit (Brain 审核提交时)                        │
  │ onError (执行异常时)                                     │
  └─────────────────────────────────────────────────────────┘

平台级事件钩子:
  ┌─────────────────────────────────────────────────────────┐
  │ onMessage (收到新消息)                                   │
  │ onTaskCreated (任务创建)                                 │
  │ onScheduleTick (定时触发)                                │
  │ onFileChanged (工作区文件变更)                            │
  │ onAgentIdle (Agent 空闲时)                               │
  └─────────────────────────────────────────────────────────┘

Hook 执行协议:
  · 同一 event 的多个 hook 按 priority ASC 顺序执行
  · 返回值:
    { action: 'pass' }                    — 放行，继续下一个 hook
    { action: 'flag', reason: '...' }     — 标记警告，继续执行
    { action: 'block', reason: '...' }    — 阻止执行，中断链路
    { action: 'modify', data: {...} }     — 修改数据后继续
  · 任一 hook 返回 'block' → 整个操作终止，返回 block reason
  · 'modify' 的 data 传递给下一个 hook（链式修改）
  · hook 异常 → 跳过该 hook，记录 failure_count
```

### 6.28 记忆仓库与共享机制

```
三层记忆模型（从内到外）:

  ┌─ Global Memory ──────────────────────────────────┐
  │  全局助手的记忆（跨所有团队可见）                    │
  │  例: "用户是夜猫子，别早上打扰" "用户偏好简洁风格"  │
  │                                                   │
  │  ┌─ Team Shared Memory ────────────────────────┐  │
  │  │  团队共享（同 workspace 内所有 Agent 可读）    │  │
  │  │  例: "客户喜欢数据先行" "品牌色 #FF6B35"      │  │
  │  │                                             │  │
  │  │  ┌─ Agent Private Memory ────────────────┐  │  │
  │  │  │  个人积累（只有自己能读写）              │  │  │
  │  │  │  例: "我上次用排比句被退回了"            │  │  │
  │  │  └──────────────────────────────────────┘  │  │
  │  └─────────────────────────────────────────────┘  │
  └───────────────────────────────────────────────────┘

可见性层级:
  private → assigned → workspace → global
     ↑          ↑           ↑          ↑
  自进化默认   手动指派    手动提升    全局助手/跨团队提升

三层存储架构:
  · agent_memories — 原始学习数据（进化过程的中间态，纯内部）
  · workspace_memories — 毕业后的记忆仓库（可验证、可团队内分享、可注入）
  · global_memories — 跨团队全局记忆（全局助手持有，所有 Agent 可按相关度读取）

| 层级 | 谁写入 | 谁能读 | 典型内容 |
|------|--------|--------|----------|
| Agent Private | Agent 自己的 L2 learning | 仅自己 | 个人经验、失败教训、角色特有技巧 |
| Team Shared | 负责人/成员提炼后提升 | 同 workspace 全员 | 项目规范、客户要求、品牌指南 |
| Global | 全局助手提炼 / 跨团队提升 | 所有 Agent（跨团队） | 用户习惯、全局规则、跨团队知识 |

写入判定机制（Brain 自动分类）:
  Agent 学到新记忆后 → Brain 判断可见性:
    · "我个人的经验/失败" → private memory
    · "团队都该知道的" → 提交 team shared（经负责人审核后入库）
    · "所有团队都适用" → 上报全局助手 → 全局助手确认后入 global_memories
```

#### 记忆类型与共享适用性

```
| 类型 | 含义 | 共享场景 |
|------|------|----------|
| knowledge | 领域事实 | "公司财年4月开始" → 全团队都该知道 |
| preference | 用户偏好 | "老板喜欢数据先行" → 所有面向用户的 Agent 都该知道 |
| feedback | 纠正/标准 | "发布前必须过法务" → 团队规范 |
| context | 上下文知识 | "当前在做 Q2 营销campaign" → 团队共享背景 |

注意: type='skill' 不再进入记忆仓库（已迁移到 plugins 统一插件系统）
```

#### 记忆生命周期

```
1. 进化产生（自动）
   Agent 执行完成 → L2 learning 分析对话轨迹 → 提取记忆
   → 写入 agent_memories (type=knowledge/preference/feedback)
   → 达到发布阈值时自动入 workspace_memories:
       条件: importance ≥ 0.5 AND access_count ≥ 2（被回忆过 2 次且仍有效）
   → 创建 memory (visibility='private', owner_agent_id=该Agent)
   → 自动创建 binding (source='self', enabled=true)

2. 私有使用（默认）
   Agent 执行时: 查询自己绑定的记忆 → 按相关度匹配 → 注入 prompt
   → 只有自己能看到和使用
   → 随着使用不断验证（被引用 = 正反馈）

3. 手动分享（用户操作）
   用户在记忆仓库 UI → "分享给 Agent X"
   → 创建 agent_memory_bindings (source='assigned')
   → Agent X 执行时可召回该记忆

4. 团队全局化（用户操作）
   用户选择某记忆 → "设为团队全局"
   → memory.visibility = 'workspace'
   → 同 workspace 所有 Agent 执行时可按相关度召回
   → 适合: 团队规范、项目级知识、团队全员应知信息

5. 跨团队全局化（用户操作 / 全局助手自动）
   用户选择某记忆 → "提升为全局" / 全局助手识别出跨团队通用知识
   → 写入 global_memories (origin='promoted', source_memory_id=原记忆)
   → 所有 workspace 的所有 Agent 执行时可按相关度召回
   → 适合: 用户习惯、全局工作规则、跨团队通用知识

   自动提升条件（满足任一即触发，需用户确认）:
     a. 跨团队重复: ≥2 个 workspace 独立产生语义相似记忆（相似度 ≥ 0.85）
     b. 全局助手自学: 全局助手在跨团队对话中提取到用户级偏好/知识
     c. 用户行为一致性: 用户对 ≥3 个团队的 Agent 做过相同纠正

   防误提升（不自动提升的情况）:
     · 团队特有术语（仅在该团队语境有意义）
     · 与特定项目/客户绑定的上下文记忆
     · importance < 0.6 的低置信度记忆
     · 已归档或标记过时的记忆

   确认流程:
     全局助手检测到可提升记忆 → 推送通知给用户:
       "发现跨团队通用知识: '{content摘要}' — 是否提升为全局记忆？"
       → 用户确认 → 写入 global_memories
       → 用户拒绝 → 标记该记忆不再候选（下次不提醒）

6. 手动创建（用户操作）
   用户在仓库中手动编写记忆 → 入库
   → origin='manual', 可指定 visibility 和绑定目标
   → 全局记忆也支持手动创建（在全局记忆管理页）
   → 适合: 直接将已知信息录入给特定 Agent 或全局
```

#### 记忆注入逻辑（区别于技能注入）

```
技能注入 = 全量 Top N（按 importance 排序截断）
记忆注入 = 按相关度检索（不是全量灌入）

Agent 执行前:
  1. 构建检索 query: 来自当前 input_prompt + 任务描述
  2. 检索候选记忆池（三层合并）:
     a. 自己绑定的 (agent_memory_bindings WHERE agent_id=X AND enabled=true)
     b. workspace 团队共享的 (visibility='workspace', 未被自己禁用的)
     c. 全局记忆 (global_memories WHERE user_id=当前用户 AND archived=0)
  3. 相关度匹配:
     · 使用 FTS5 全文检索: content MATCH :query
     · 按 rank (BM25) + importance 加权排序
     · 来源层级加权: global ×1.1, workspace ×1.0, private ×0.9
       （全局记忆略高权重 — 代表用户级别的确认）
     · 取 Top K 条（默认 K=12，受 token 预算限制）
  4. 注入格式:
     ---
     ## 相关记忆（自动召回）

     - [全局·偏好] {content}              ← global_memories
     - [团队·知识] {content}              ← workspace_memories (visibility=workspace)
     - [个人·规范] {content}              ← agent_memory_bindings (private)
     ---

  5. Token 预算:
     · 记忆注入共享技能的 10% 预算（即 context window 的 10% 由技能+记忆分享）
     · 默认: 技能占 6%，记忆占 4%（含三层记忆总和）
     · 可在 agent.config 中调整比例: skill_budget / memory_budget

  与 workspace.context 的关系:
     · workspace.context = 静态上下文（手写的团队 README，始终全量注入）
     · workspace_memories = 团队动态知识（不断积累，按相关度检索注入）
     · global_memories = 跨团队用户级知识（用户习惯、全局规则）
     · 三者共存不冲突: context 是"必须知道的"，memories 是"相关时才想起来的"
```

#### 记忆过时与清理

```
记忆与技能不同: 技能通常不会过时（写文案的方法论长期有效），
但记忆可能过时（"本季度目标是 X" 下季度就变了）。

过时检测:
  · 时间衰减: knowledge/context 类型 90 天未被召回 → importance -= 0.1/月
  · preference/feedback 不自动衰减（行为偏好通常稳定）
  · 手动标记: 用户/上级可标记某记忆为"已过时" → importance = 0, 不再注入
  · 冲突检测: 如果新记忆与旧记忆矛盾（简单关键词重叠 + 语义否定）
    → 提示用户确认哪个有效

自动清理:
  · importance = 0 且 90 天未被任何人引用 → 归档（不删除，移到 archived 状态）
  · 归档的记忆在仓库中折叠显示，可恢复

与技能的对比:
  | 维度 | 技能 | 记忆 |
  |------|------|------|
  | 注入方式 | Top N 全量 | 相关度检索 |
  | 过时风险 | 低（方法论稳定） | 高（事实会变） |
  | 版本管理 | 有（v1/v2/v3） | 无（直接编辑） |
  | 核心价值 | "怎么做" | "知道什么" |
  | 衰减速度 | 慢（30天不用 -0.1） | 快（90天不召回 -0.1/月） |
```

#### 与 workspace.context 的协作

```
四种"知识注入"方式的定位:

  1. workspace.context (TEXT 字段)
     · 静态、手写、始终全量注入
     · 适合: 团队介绍、术语表、核心规范、不变的背景
     · 谁写: 用户手动编辑（workspace 设置页）
     · 大小: ≤ context window 5%

  2. global_memories (跨团队全局)
     · 动态、积累、按相关度检索注入
     · 适合: 用户习惯、全局规则、跨团队通用知识
     · 谁写: 全局助手提炼 / 从 workspace_memories 提升 / 用户手动
     · 大小: 单次注入 ≤ context window 2%

  3. workspace_memories (visibility='workspace')
     · 动态、积累、按相关度检索注入
     · 适合: 团队内发现的新知识、客户偏好、项目上下文
     · 谁写: Agent 自进化 + 用户手动 + 从私有提升
     · 大小: 单次注入 ≤ context window 2%

  4. agent_memories (纯私有内部状态)
     · 进化过程的中间数据，不直接注入
     · 通过发布到 workspace_memories 后才对外生效
     · 保留用于: 进化算法的输入数据、学习轨迹追溯

  组装顺序（Prompt 裁剪策略第 3-4 层更新）:
    层3 [高优]: workspace.context (静态，全量)
    层4 [中优]: plugins (prompt facet，Top N)
    层4.5 [中优]: 三层记忆合并检索 (global + workspace + private, Top K)
    → 层 4 + 4.5 共享 10% 预算，按 skill_budget/memory_budget 配比分配
```

### 8.1 看板系统详细设计

#### 任务卡片字段

| 字段 | 说明 |
|------|------|
| 标题 | 任务简述 |
| 描述 | Markdown 富文本，支持代码块、图片引用 |
| 状态列 | 用户自定义（默认：待办/进行中/审核中/已完成） |
| 发起人 | 谁创建的这个任务（用户或上级 Agent） |
| 责任人 | 谁执行这个任务（Agent 或用户），支持多人 |
| 优先级 | 低/中/高/紧急，颜色标识 |
| 截止时间 | 可选 deadline |
| 子任务 | 支持任务嵌套（父任务 → 子任务） |
| 标签 | 自定义标签分类 |
| 工时估算 | 预估/实际工时 |

#### 看板交互

- **拖拽排序** — 任务在列内拖拽重排序（@dnd-kit）
- **跨列移动** — 拖拽到其他状态列 = 状态变更
- **批量操作** — 多选后批量移动/删除/分配（底部浮动 Action Bar）
- **筛选过滤** — 按责任人、优先级、标签、时间、依赖状态筛选
- **保存视图** — 筛选条件保存为命名视图，一键切换
- **搜索** — 全局任务搜索（标题 + 描述 + 评论，FTS5 全文检索）
- **视图切换** — 四种视图自由切换:
  - Board（看板）— 列+卡片，默认
  - List（列表）— 表格形式，支持排序/分组/展开子任务
  - Gantt（甘特图）— 时间轴 + 依赖箭头连线 + 里程碑
  - Timeline（时间线）— 按时间倒序的活动流
- **依赖可视化** — 被阻塞的卡片置灰+锁图标，Gantt 中箭头连线
- **Reactions** — 任务卡片和评论支持 emoji 反应（点击即加）
- **验收清单** — 任务详情中展示 acceptance_criteria checklist（可勾选）

#### 任务生命周期

```
创建 → 待办 → 进行中 → 审核中 → 已完成 → 已归档
                ↑         │
                └──── 退回重做
        │
        └───→ 已阻塞 (用户手动)

自动流转（执行引擎驱动，无需人工干预）:
  待办→进行中: job_queue claim 时
  进行中→审核中: Agent execution 完成时
  审核中→已完成: 上级 approve 时
  审核中→进行中: 上级 reject 时（Agent 重做）

手动流转（用户看板拖拽）:
  任意方向拖拽均可（用户有最高权限）
  拖到「已完成」= 跳过审核，强制完成
  拖到「待办」= 暂停执行，移出队列
```

#### 评论系统

- **Markdown 评论** — 支持代码块、引用、列表
- **Agent 执行结果自动提交为评论** — 包含输出文本 + 耗时 + Token 消耗
- **附件上传** — 图片、文件、代码文件
- **@提及** — 在评论中 @其他 Agent 或用户
- **评论时间线** — 按时间倒序显示所有活动

#### 内置工具（bundled 插件）

以下工具作为 `source='bundled'` 的 tool-facet 插件预装:

| 插件名 | 工具 | 说明 |
|--------|------|------|
| builtin-filesystem | file_read, file_write, file_list | workspace 文件操作 |
| builtin-web | web_search, web_fetch | 互联网搜索与抓取 |
| builtin-code | code_execute | 沙箱代码执行 |

#### MCP Bridge（兼容接入）

```
现有 MCP 服务器通过 source='mcp-bridge' 自动桥接为插件:

  配置方式:
    · User/Workspace/Agent 三级配置 MCP endpoint
    · 系统自动生成对应的 mcp-bridge 插件
    · 每个 MCP tool → plugin_tools 表中的一条记录

  三层继承不变（通过 plugin scope 实现）:
    User 级 MCP config   → mcp-bridge plugin (scope='global')
    Workspace 级         → mcp-bridge plugin (scope='workspace')
    Agent 级             → mcp-bridge plugin (scope='private')

  合并规则同插件系统:
    · 默认 merge: 三层叠加
    · 同名工具: Agent > Workspace > User
    · 可通过 agent_plugin_bindings.enabled=0 禁用继承的 MCP 插件
```

#### 工具访问控制

```
通过 agent.config.plugin_override 控制:

  // 只允许特定插件的工具
  plugin_override: {
    mode: 'merge',
    disabled: ['builtin-web'],  -- 禁止该 Agent 上网
  }

  // 完全隔离（只用自己绑定的）
  plugin_override: {
    mode: 'replace',
  }

工具调用审计:
  · 每次工具调用记录到 tool_calls 表: plugin_name, tool_name, input, output, duration
  · Brain 审核时可查看完整工具调用链
  · 高危工具（permission_scope='dangerous'）每次调用需 Brain 批准
```

## 十一、关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 对话入口 | 全局助手 (委托制) | 统一入口、跨团队路由、不审核不做瓶颈 |
| 数据库 | SQLite | 零依赖、单文件备份、自托管友好 |
| 队列 | SQLite 轮询 (中央派发) | 避免 Redis，单进程调度器全局视角 |
| 任务分配 | 指派制 + 可选池认领 | 默认上级指派，同角色多人时按策略认领 |
| 审核模型 | 轻量独立 LLM 调用 | 不占会话锁、不入队、可并发、30s 超时 |
| 组织树 | Materialized Path + Adjacency | CTE 递归查询 + path 前缀查子树 |
| Agent 分配 | 多态 (type + id) | 统一 agent/user/role 分配 |
| 文件存储 | 本地 FS | Docker volume 挂载，简单可靠 |
| 实时 | Electron IPC + EventEmitter | 同进程零网络开销，实时事件直接 push |
| 双运行时 | Bun 唯一运行时 | 不再兼容 Node，Electron 主进程用 Bun |
| 前端复用 | Electron + React + MUI（参考 Multica） | 桌面应用（Berry 实际为 Web SPA + HeroUI v3） |
| 执行流式 | AsyncGenerator | Agent 输出实时推送到前端 |
| 通知 | 站内 + Electron IPC + 系统通知 | 桌面应用原生通知，后续扩展 Webhook |
| 断点恢复 | Checkpoint + Resume | 提升可靠性，transient 故障自动恢复 |
| 任务依赖 | finish_to_start + 防环检测 | 复杂项目需要依赖关系 |
| 触发源 | Cron + Webhook + Event 三合一 | 覆盖所有自动化触发场景 |
| 并发策略 | queue/replace/forbid | 避免重复触发导致资源浪费 |
| 错误分类 | 4 级分类 (transient/permanent/resource/timeout) | 智能决定重试策略，减少无效重试 |
| 全局搜索 | FTS5 全文检索 | SQLite 原生支持，无需 ES |
| 任务编号 | workspace 级自增 `{prefix}-{N}` | 人类可读、跨项目唯一、避免全局锁 |
| 评论线程 | parent_id + resolved_at | 支持嵌套讨论、标记已解决，Multica 验证模式 |
| 准入检查 | Admission Gate (skipped ≠ failed) | 前置检查 Agent 状态/配置，避免无效执行占队列 |
| 自动暂停 | 7 天回溯 50+次 90%+ 失败 → pause | 防止持续浪费 token，Multica 经验数据阈值 |
| 通知订阅 | 自动订阅 + 手动 + 分组偏好 | 创建者/指派人/评论者自动订阅，用户可按组静音 |
| 重复检测 | 标题归一化 + 悲观锁 | 自动化高频创建时防重复，不依赖唯一索引 |
| 工作目录复用 | prior_session_id + prior_work_dir | Agent 断点续做时保留工作现场，减少上下文重建 |
| 思考级别 | per-agent 4 级 (low/medium/high/max) | 替代布尔开关，精细控制 token 消耗与推理深度 |
| 执行模式 | create_task vs run_only | Cron 可直接执行不产生看板卡片，适合定时清理等 |
| Usage 聚合 | 按小时 (workspace, agent, model) 汇总 | 分析成本趋势，避免逐条查询执行记录 |
| Agent 软删除 | archived_at + archived_by | 保留历史引用完整性，可恢复 |
| 位置排序 | REAL 浮点数 | 拖拽插入只需 (a+b)/2，不必批量 reindex |
| 任务元数据 | JSONB (50 key, 8KB) | 灵活自定义字段，原子单 key 更新，有上限防滥用 |
| Workspace 上下文 | 全局注入 system prompt | 所有 Agent 共享工作区级别领域知识 |
| 信任等级 | 4 级 (probation→standard→trusted→autonomous) | 审核成本翻倍问题，用信任升级换取 60-70% 审核节省 |
| 全局助手降级 | 重试→手动选团队→可选关键词匹配 | 单点路由层故障不应阻塞全部用户交互 |
| SQLite 写策略 | 单写者 + busy_timeout 5s + BEGIN IMMEDIATE | 避免 SQLITE_BUSY，接受单进程硬约束 |
| 链路追踪 | trace_id 全链路传播 | 复杂触发链（webhook→chain→fanout→review）需要端到端可观测 |
| Prompt 裁剪 | 6 层优先级 + 按层截断 | 多源 prompt 组装容易溢出 context window |
| 数据备份 | 每日热备 + 7/4/6 保留策略 | SQLite 单文件一损全损，RPO ≤ 24h |
| 数据归档 | 90 天 executions 移 archive.db | 控制主库大小 ≤ 2GB，保持查询性能 |
| 容量上限 | ≤ 200 Agent / ≤ 20 并发执行 | 单进程 + SQLite 天花板，明确边界避免误用 |
| 统一插件系统 | Multi-Facet Plugin（prompt/tool/code/hook/service）| 取代 Skills+MCP+工具+自进化插件四套机制，原子化 + 解耦 + scope 继承 |
| 插件安全 | Worker 沙箱 + 声明式权限 + 分级审批 | 自进化产出的代码不可信，必须隔离执行 + 权限限制 |
| MCP 兼容 | mcp-bridge source 自动桥接 | 已有 MCP 生态不废弃，统一管理但透明接入 |
| 记忆分享 | 三层模型: private → team → global | 不同知识有不同的适用范围，Brain 自动判定层级 |
| 记忆注入 | FTS5 三层合并检索 Top K | 记忆量大不能全量灌入，三层按当前任务匹配最相关的 |
| 记忆 vs 技能 | 分开管理，各自独立仓库 | "怎么做"(技能) vs "知道什么"(记忆) 语义不同，注入策略也不同 |
| Workspace 删除 | 软删除 + 14 天 grace period | 防误删，永久删除不可逆需要缓冲期 |
| Workspace 归档 | 冻结所有执行，数据保留可恢复 | 不丢数据但释放运行资源，与删除是独立操作 |
| 所有权转让 | 转让后原 owner 降为 admin | 简化权限模型，不支持共同所有者 |
| Runtime 架构 | Driver 模式 + 统一 AgentRuntime 接口 | 解耦执行引擎与具体 Agent 运行时，新增 provider 只需实现接口 |
| 外部 Runtime 审核 | 只审核最终输出，不拦截中间步骤 | 外部 Runtime（CC/opencode）有独立工具链，拦截中间步骤不现实也不必要 |
| 外部 Runtime 通信 | spawn 子进程 / HTTP API | 本地 CLI 工具用子进程，远程服务用 HTTP SSE |
| Runtime 安全边界 | 文件隔离 + 环境过滤 + 超时 + 输出审核 | 全权执行≠无限制，通过 OS 级隔离和审核兜底 |
| API Key 管理 | 三层继承 (Agent→Workspace→User) + AES-256 加密 | 多 Agent 共享 Key 是常态，集中管理避免散落 |
| 委托模型 | 异步委托 + 实时推送结果 | 团队任务可能耗时几分钟到小时，同步等待不现实 |
| Session 生命周期 | 按类型区分（chat/execution/chain/delegate） | 不同场景的 session 生存规则完全不同 |
| Session 并行 | 同 Agent 同时最多 1 个 execution session | 会话锁保证上下文不串，user_chat 可与 execution 共存 |
| 并发冲突 | 用户操作优先 + 乐观锁 (version) | 人是最终决策者，系统操作可被人覆盖 |
| Context 传播 | 冻结快照，下次执行时自然生效 | 执行中改 context 不应打断正在进行的工作 |
| 外部 Runtime 崩溃 | 进程 exit 检测 + SIGTERM/SIGKILL 超时 | 外部进程不可控，必须有强制终止机制 |
| 文件权限 | Agent 私有目录读写 + shared/ 有条件写 | 简单粗粒度隔离，MVP 够用 |
| 用户角色权限 | owner > admin > member 三级 | 多人协作需要差异化权限，但不要过度复杂 |

## 十三、容量规划与系统约束

### 硬性约束

| 约束 | 上限 | 原因 |
|------|------|------|
| 部署模式 | 单进程桌面应用 (Electron) | SQLite 不支持多实例并发写 |
| 并发用户 | ≤ 5 | IPC 通道 + 实时推送负载 |
| Workspace 数量 | ≤ 100/用户 | SQLite 文件大小和查询性能 |
| Agent 总数 | ≤ 200/实例 | 内存中维护状态 + 调度器轮询效率 |
| 并发执行 Agent | ≤ 20 | LLM API 并发限流 + 单进程 CPU |
| 队列深度 | ≤ 500 pending | SQLite 轮询 2s 内必须扫完 |
| 数据库文件 | ≤ 2GB | SQLite 实践中超过后查询劣化 |
| 单 Agent 工作目录 | ≤ 500MB | 磁盘空间管控 |

### 典型场景容量预估

```
场景 A: 个人用户（1 人 2 团队）
  · 2 workspace × 5 Agent = 10 Agent
  · 日执行: ~20 次
  · 日审核: ~14 次 (trusted Agent 跳过 30%)
  · 日 Token: ~100k tokens (~$1.5/天)
  · 数据库: <50MB/月

场景 B: 小团队（3 人 5 团队）
  · 5 workspace × 8 Agent = 40 Agent
  · 日执行: ~80 次
  · 日审核: ~40 次 (trust-based 模式)
  · 日 Token: ~400k tokens (~$6/天)
  · 数据库: <200MB/月

场景 C: 压力边界（1 人 20 团队，重度自动化）
  · 20 workspace × 10 Agent = 200 Agent
  · 日执行: ~500 次（大量 cron）
  · 日审核: ~150 次（auto-approve 生效）
  · 日 Token: ~2M tokens (~$30/天)
  · 数据库: ~1GB/月 → 需定期归档
```

### 超限处理

```
Agent 数量超限:
  · 创建第 201 个 Agent 时提示"已达上限"
  · 建议归档不活跃的 Agent

队列积压超限:
  · pending > 500 → 拒绝新入队，返回 429
  · 通知用户: "任务队列已满，请等待或清理"

数据库过大:
  · 监控 db_size_mb 指标
  · 超过 1.5GB → 告警
  · 自动归档: 90 天前的 executions 移到 archive.db
  · 用户可手动导出+清理

磁盘空间不足:
  · 按 last_active_at 清理最久未用的 Agent 工作目录
  · 先清 output/ 再清 code/（保留 prompts/）
```

## 十四、执行链路追踪

### Trace ID 机制

```
每次用户操作或外部触发产生一个 trace_id，所有因此产生的 execution 共享:

  trace_id 生成时机:
    · 用户发消息 → 全局助手或 Agent 处理 → trace_id = nanoid()
    · Cron 触发 → trace_id = 'cron:{job_id}:{timestamp}'
    · Webhook 到达 → trace_id = 'wh:{delivery_id}'
    · Event 触发 → trace_id = 'evt:{event_id}:{timestamp}'

  传播规则:
    · 负责人拆解创建子任务 → 子任务 execution 继承 trace_id
    · 链式触发 (chain) → 继承上一环节的 trace_id
    · fan-out 广播 → 所有分支共享同一 trace_id
    · 审核调用 → 继承被审 execution 的 trace_id
    · 退回重做 → 新 execution 继承原 trace_id（同一条链）

  数据模型:
    agent_executions 新增:
      trace_id TEXT  -- 全链路追踪 ID (同一用户操作触发的所有 execution 共享)

    索引: CREATE INDEX idx_executions_trace ON agent_executions(trace_id)

  查询用途:
    · "这条消息最终触发了哪些 Agent？" → WHERE trace_id = :id
    · "这个 webhook 的完整处理链路？" → 按 trace_id 聚合 + started_at 排序
    · "为什么这个任务失败了？" → 追溯 trace_id 找到失败的环节
    · 前端: 点击某条通知 → 展开完整追踪链（timeline 形式）

  可视化:
    · 链路视图: trace_id → 展示所有 execution 的有向图
    · 根节点: 用户消息/cron 触发/webhook
    · 边: execution → 下一个 execution (chain/fanout/decompose)
    · 每个节点标注: agent_name + status + duration_ms
```

## 十五、Prompt 组装与裁剪策略

### Prompt 组装层级

```
Agent 执行时 system prompt 由以下层级组装（优先级从高到低）:

  1. [必须] Agent 基础 system_prompt — agent.config.system_prompt
     · 角色定义、行为约束、工具使用规则
     · 不可裁剪（核心人设）

  2. [必须] 任务指令 — 当次 execution 的 input_prompt
     · 用户消息 / cron prompt / chain prompt
     · 不可裁剪（核心指令）

  3. [高优] Workspace 上下文 — workspace.context
     · 团队级领域知识、术语表、规范
     · token 预算: context window 的 5%
     · 超出时截断尾部

  4. [中优] 技能注入 — agent_memories (type='skill')
     · 已学技能按 importance 排序注入
     · token 预算: context window 的 10%
     · 超出时按 importance 截断低优先级技能

  5. [中优] 审核反馈上下文 — 退回重做时注入
     · 上级 guidance + 上次输出（作为反面参考）
     · token 预算: context window 的 15%
     · 超出时裁剪上次输出（保留 guidance 全文）

  6. [低优] 对话历史 — session_messages
     · 多轮对话时的历史消息
     · token 预算: 填充剩余空间
     · 超出时触发上下文压缩（6.9 机制）

裁剪算法:
  total_budget = model_context_window × 0.85  (预留 15% 给模型输出)
  used = 0
  for layer in [1, 2, 3, 4, 5, 6]:
    if used + layer_tokens <= total_budget:
      include(layer)
      used += layer_tokens
    else:
      truncate(layer, remaining=total_budget-used)
      break

安全约束:
  · 层级 1 + 2 总和 > 总预算 → 报错（不执行），通知用户缩短 prompt
  · 单次执行前计算总 token 估算，写入 execution 记录
  · 前端可预览"Prompt 预算分配"（调试用）
```

## 十六、数据备份与迁移

### 备份策略

```
SQLite 单文件 = 一损全损。备份是生命线:

  自动备份:
    · 每日凌晨 3:00 — 全量备份（SQLite .backup API，在线热备）
    · 备份前执行 PRAGMA integrity_check（确认数据库完好）
    · 备份文件: data/backups/platform-{date}.db.gz（gzip 压缩）
    · 保留策略: 最近 7 天每日 + 每周一份保留 4 周 + 每月一份保留 6 个月

  工作目录备份:
    · 只备份 shared/ 和 agents/ 下的 prompts/ 目录
    · 不备份 output/、code/（可重新生成）
    · 周期: 每周一次

  备份位置:
    · 本地: {userData}/backups/ (Electron app data 目录)
    · 可选: 配置外部存储 (S3/WebDAV/本地其他磁盘)
    · 设置项: 备份路径、远程 URL

  恢复流程:
    1. 停止服务
    2. 替换 data/platform.db 为备份文件
    3. 重启服务
    4. 验证: API health check + 最近 execution 记录是否存在

  灾难恢复 RTO/RPO:
    · RPO (数据丢失): ≤ 24 小时（每日备份）
    · RTO (恢复时间): < 5 分钟（替换文件+重启）
```

### Schema 迁移策略

```
Drizzle ORM 提供 schema diff 能力，但需要明确流程:

  开发环境:
    · drizzle-kit push (直接同步 schema 到 SQLite)
    · 不生成迁移文件（快速迭代）

  生产环境:
    · drizzle-kit generate (生成 SQL 迁移文件)
    · 迁移文件存放: packages/platform-api/drizzle/
    · 启动时自动检测并执行未应用的迁移
    · 迁移前自动创建备份（兜底）

  版本跟踪:
    · _drizzle_migrations 表记录已应用的迁移
    · 每次 schema 变更 = 新迁移文件 + 版本号递增

  破坏性变更处理:
    · 删列/改类型: 先新增列 → 数据迁移 → 再删旧列（分步）
    · 不允许 DROP TABLE（只允许 archive + 新建）
    · 大表 ALTER: 可能锁库数秒，在备份窗口执行

  回滚:
    · 每个迁移文件配对一个 rollback SQL
    · 实际回滚场景罕见（更常见的是 restore backup + 修复后重新迁移）

  应用升级流程:
    1. electron-updater 下载新版本
    2. 新版本启动时自动执行 pending migrations
    3. 迁移失败 → 拒绝启动 + 弹窗告警
    4. 用户恢复备份 → 报 issue → 等修复版本
```

### 数据归档

```
老数据持续增长会拖慢查询，需要定期归档:

  归档规则:
    · agent_executions: >90 天 → 移到 archive.db
    · session_messages: >60 天（已 compressed 的会话）→ 归档
    · webhook_deliveries: >30 天 → 归档
    · usage_hourly: >90 天 → 聚合为 daily 后删除明细
    · notifications: >30 天且已读 → 删除

  归档方式:
    · INSERT INTO archive.platform_archive SELECT ... FROM agent_executions WHERE ...
    · DELETE FROM agent_executions WHERE id IN (已归档的 IDs)
    · VACUUM（可选，回收空间但会锁库）

  归档触发:
    · 每周日凌晨 4:00 自动执行
    · 或 db_size_mb > 1500 时触发紧急归档
    · 归档期间服务可用（WAL 模式允许并发读）

  归档数据查询:
    · 前端默认不展示归档数据
    · 高级查询: ATTACH 'archive.db' AS archive → 跨库查询
    · 或提供"查看历史记录"按钮 → 加载归档数据
```

## 十七、Workspace 完整生命周期

### 状态机

```
                 ┌─────────────────────────────────────┐
                 │                                     ▼
  [创建] ──→ active ──→ archived ──→ deleted (grace period) ──→ 永久销毁
                 ▲           │
                 └───────────┘
                  (restore 恢复)
```

| 状态 | 含义 | 可执行操作 |
|------|------|-----------|
| `active` | 正常运行 | 全部功能可用 |
| `archived` | 冻结归档 | 只读、不可执行、不可调度、可恢复 |
| `deleted` | 待销毁（14 天 grace period） | 不可访问、仅 owner 可撤销 |

### 数据模型扩展

```sql
workspaces 表新增字段:
  status       TEXT NOT NULL DEFAULT 'active'  -- 'active' | 'archived' | 'deleted'
  archived_at  INTEGER       -- 归档时间戳
  archived_by  TEXT          -- 执行归档的用户 ID
  deleted_at   INTEGER       -- 标记删除时间戳（grace period 起点）
  transferred_at INTEGER     -- 最近一次转让时间
```

---

### 17.1 创建流程

```
触发方式:
  · 手动创建: POST /api/workspaces/create {name, description, context?}
  · AI 建团队: 全局助手调用 create_workspace 工具 → 自动填充配置

创建步骤:
  1. 写入 workspaces 表 (status='active')
  2. 创建 workspace_members 记录 (当前用户, role='owner')
  3. 自动创建根 org_node (名称 = workspace name)
  4. 自动创建顶层负责人 Agent (superior_id=NULL, agent_type='team')
  5. 创建文件系统目录: data/workspaces/{id}/shared/
  6. 若 AI 建团队 → 继续生成组织结构 + Agent 配置

默认值:
  · issue_prefix: 从 name 中提取大写首字母（最长 5 字符）
  · review_mode: 'trust_based'
  · context: 空（后续可编辑）
```

### 17.2 归档流程

```
触发: POST /api/workspaces/:id/archive
权限: owner 或 admin

归档执行:
  1. 检查是否有 running 状态的 execution → 有则拒绝（"请等待执行完成或取消"）
  2. 更新 workspaces: status='archived', archived_at=now, archived_by=user_id
  3. 暂停所有 cron_jobs (status → 'paused', 记录 paused_reason='workspace_archived')
  4. 暂停所有 webhook_endpoints (active=false)
  5. 设置所有 Agent: agent_status='paused'（不是 archived，区别于 Agent 级归档）
  6. 清理队列: 移除该 workspace 下所有 pending 任务，标记为 'cancelled'
  7. 发送通知给所有 workspace_members: "工作空间已归档"

归档后行为:
  · 所有数据保留，可查看但不可修改
  · Agent 不会被调度执行
  · 看板只读，任务不可创建/移动
  · 文件系统不删除
  · 不占用 "并发执行" 配额
  · API 返回 403 + error='workspace_archived' 对任何写操作

恢复: POST /api/workspaces/:id/restore
  1. 更新 workspaces: status='active', archived_at=NULL, archived_by=NULL
  2. Agent status 恢复为 'idle'
  3. Cron/Webhook 不自动恢复（需手动启用，防止意外触发）
  4. 发送通知: "工作空间已恢复"
```

### 17.3 删除流程

```
触发: POST /api/workspaces/:id/delete
权限: 仅 owner
前提: status 可以是 'active' 或 'archived'

删除执行（软删除 + Grace Period）:
  1. 若 status='active' → 先执行归档流程全部步骤
  2. 更新 workspaces: status='deleted', deleted_at=now
  3. 发送通知给所有成员: "工作空间将在 14 天后永久删除"
  4. 工作空间从所有列表中隐藏（除 owner 的"已删除"视图）

Grace Period (14 天):
  · Owner 可在 /settings/deleted-workspaces 中看到
  · 可撤销: POST /api/workspaces/:id/restore → 恢复到 archived 状态
  · 14 天后由定时任务执行永久删除

永久删除（不可逆）:
  1. 删除 workspace 文件目录: data/workspaces/{id}/ (rm -rf)
  2. 级联删除数据库记录（按顺序）:
     · session_messages (通过 agent_id 关联)
     · agent_executions (通过 agent_id 关联)
     · agent_memories (通过 agent_id 关联)
     · plugins + plugin_tools + plugin_hooks + agent_plugin_bindings
     · workspace_memories + agent_memory_bindings
     · tasks + task_comments + task_attachments (通过 project_id)
     · projects + project_columns
     · agents (通过 workspace_id)
     · org_nodes (通过 workspace_id)
     · cron_jobs + webhook_endpoints (通过 workspace_id)
     · workspace_members
     · notifications (相关的)
     · workspaces 记录本身
  3. 归档数据: archive.db 中该 workspace 相关记录也删除
  4. 写入审计日志: "workspace {name} permanently deleted by {user}"
  5. VACUUM（可选，非高峰期执行）

安全措施:
  · 删除前弹窗确认: 输入 workspace name 才能确认
  · 删除后 24 小时内发送邮件提醒（如配置了邮件）
  · 永久删除前检查: deleted_at + 14 天 < now
```

### 17.4 转让所有权

```
触发: POST /api/workspaces/:id/transfer {new_owner_id}
权限: 仅当前 owner

前置检查:
  · new_owner_id 必须是 workspace_members 中的现有成员
  · workspace 状态必须是 active（归档/删除中的不能转让）
  · new_owner_id 不能是当前 owner（无意义操作）

转让步骤:
  1. 更新 workspace_members: 原 owner role → 'admin'
  2. 更新 workspace_members: 新 owner role → 'owner'
  3. 更新 workspaces: owner_id = new_owner_id, transferred_at = now
  4. 发送通知给新 owner: "你已成为 {workspace.name} 的所有者"
  5. 发送通知给原 owner: "你已将 {workspace.name} 转让给 {new_owner.name}"
  6. 写入审计日志

转让不变更:
  · Agent 配置/归属不变
  · 文件系统不变
  · 组织结构不变
  · 所有调度/webhook 不变
  · 成员列表（除角色变化外）不变

限制:
  · 每个 workspace 同一时间只有一个 owner
  · 转让后原 owner 降为 admin（保留管理权限）
  · 不支持"共同所有者"（简化权限模型）
```

### 17.5 API 汇总

```
已有:
  POST /api/workspaces/create          # 创建
  POST /api/workspaces/:id/update      # 更新（name/description/context/review_mode）
  POST /api/workspaces/:id/delete      # 软删除（进入 grace period）

新增:
  POST /api/workspaces/:id/archive     # 归档（冻结）
  POST /api/workspaces/:id/restore     # 恢复（从 archived 或 deleted 恢复）
  POST /api/workspaces/:id/transfer    # 转让所有权 {new_owner_id}
  GET  /api/workspaces/deleted         # 查看已删除列表（grace period 内）
  POST /api/workspaces/:id/destroy     # 立即永久删除（跳过 grace period，需二次确认）
```

### 17.6 定时任务

```
workspace_cleanup (每日凌晨 4:30 执行):
  · 扫描 status='deleted' 且 deleted_at + 14 天 < now 的 workspace
  · 逐个执行永久删除
  · 每次最多处理 5 个（避免长时间锁库）
  · 执行结果写入系统日志
```

## 十八、API Key 与 LLM 配置管理

### 配置层级

```
三层继承（就近覆盖）:

  全局默认 (用户级)
    └── Workspace 级覆盖
        └── Agent 级覆盖

查找顺序: Agent.config.api_key → workspace_llm_configs → user_llm_configs
```

### 数据模型

```sql
-- 用户级 LLM 配置（全局默认）
user_llm_configs
  id           TEXT PRIMARY KEY
  user_id      TEXT NOT NULL → users.id
  provider     TEXT NOT NULL  -- 'anthropic'|'openai'|'openrouter'|'custom'
  name         TEXT NOT NULL  -- 用户自定义名称（如"我的 Claude Key"）
  api_key_encrypted TEXT NOT NULL  -- AES-256 加密存储
  endpoint     TEXT           -- 自定义 endpoint（custom provider 必填）
  models       TEXT           -- JSON: ['claude-sonnet-4-6','claude-opus-4'] 该 key 可用的模型列表
  is_default   INTEGER NOT NULL DEFAULT 0  -- 是否为该 provider 的默认 key
  rate_limit   INTEGER        -- 自定义每分钟请求限制（避免超额）
  monthly_budget REAL         -- 月度预算上限（美元），超限告警
  current_month_cost REAL NOT NULL DEFAULT 0  -- 当月已用费用
  status       TEXT NOT NULL DEFAULT 'active'  -- 'active'|'expired'|'rate_limited'
  last_used_at INTEGER
  created_at   INTEGER NOT NULL
  UNIQUE(user_id, provider, name)

-- Workspace 级 LLM 配置覆盖（可选）
workspace_llm_configs
  id           TEXT PRIMARY KEY
  workspace_id TEXT NOT NULL → workspaces.id
  provider     TEXT NOT NULL
  config_id    TEXT NOT NULL → user_llm_configs.id  -- 引用用户的哪个 key
  model_override TEXT        -- 覆盖默认模型
  is_default   INTEGER NOT NULL DEFAULT 1
  UNIQUE(workspace_id, provider)
```

### Key 选择逻辑

```
Agent 执行时选择 API Key:

  1. agent.config.api_key_id 指定了 → 直接用（Agent 级显式绑定）
  2. workspace_llm_configs 有匹配 provider → 用 workspace 级
  3. user_llm_configs 的 is_default=1 且 provider 匹配 → 用全局默认
  4. 都没有 → 报错: "请先配置 {provider} 的 API Key"

Key 共享:
  · 同一个 user_llm_configs 记录可被多个 Agent/Workspace 引用
  · 删除 key 前检查: 是否有 Agent 正在使用 → 提示"N 个 Agent 在用此 key"
  · key 失效时: 标记 status='expired'，相关 Agent 执行时报错提示换 key
```

### 安全措施

```
存储:
  · API Key 使用 AES-256-GCM 加密存储，密钥来自环境变量 ENCRYPTION_KEY
  · 前端展示: 只显示前 4 + 后 4 位，中间 *** 掩码
  · API 返回: 永远不返回 api_key_encrypted 原文，只返回 id + 掩码

传输:
  · 创建/更新 key 的接口走 HTTPS
  · key 在内存中使用后立即清零（不缓存明文）

运行时:
  · Agent.config 中不存 api_key 明文，只存 api_key_id（引用）
  · 执行时从 user_llm_configs 实时解密

防泄露:
  · Agent 输出审核时检查: 是否包含 api key pattern（sk-xxx/key-xxx）
  · 日志中自动 redact api_key pattern
```

### 额度与预算

```
费用追踪:
  · 每次 execution 完成后累加到 user_llm_configs.current_month_cost
  · 每月 1 号自动重置 current_month_cost = 0

预算告警:
  · 80% 月预算 → 通知 "API 费用已用 80%"
  · 100% 月预算 → 通知 + 可选: 自动暂停非关键执行
  · 暂停策略: 只暂停 cron 和 fan_out，用户手动对话仍可用

Key 失效处理:
  · API 返回 401/403 → 标记 key status='expired'
  · 通知用户: "API Key 已失效，请更新"
  · 关联的 Agent 执行时自动失败并提示
  · 不自动切换 key（防止误用其他环境的 key）
```

## 十九、全局助手委托模型

### 委托生命周期

```
全局助手 delegate_to_team 后的完整流程:

  ┌─────────────────────────────────────────────────────────┐
  │  异步委托 + 实时通知（非同步阻塞）                         │
  └─────────────────────────────────────────────────────────┘

  时序:
    t0: 用户发消息 → 全局助手分析意图
    t1: 全局助手回复: "好的，已交给内容团队处理"
        → 调用 delegate_to_team(workspace_id, prompt)
        → 创建 delegation 记录
    t2: 用户可以继续跟全局助手聊其他事（不阻塞）
    t3: 目标团队负责人接手 → 内部拆解/执行/审核
    ...（可能持续几分钟到几小时）
    tN: 团队完成 → 结果回传
    tN+1: 全局助手向用户推送: "内容团队完成了你的请求，结果如下: ..."

  关键设计:
    · 委托是异步的 — 用户发消息后立即得到确认，不阻塞等待
    · 全局助手保持会话可用 — 用户可以继续对话（问其他事/委托其他团队）
    · 结果回传是推送通知 — 通过 IPC 事件推送到全局助手对话流中
```

### 数据模型

```sql
-- 委托记录
delegations
  id              TEXT PRIMARY KEY
  user_id         TEXT NOT NULL → users.id
  assistant_session_id TEXT NOT NULL → agent_sessions.id  -- 全局助手的会话
  target_workspace_id TEXT NOT NULL → workspaces.id
  target_agent_id TEXT NOT NULL → agents.id  -- 负责人
  original_prompt TEXT NOT NULL  -- 用户原始指令
  status          TEXT NOT NULL DEFAULT 'pending'
                  -- 'pending' (已委托,待处理)
                  -- 'accepted' (负责人开始处理)
                  -- 'completed' (完成,结果已回传)
                  -- 'failed' (执行失败)
                  -- 'timeout' (超时未完成)
                  -- 'cancelled' (用户取消)
  result_summary  TEXT           -- 完成后的结果摘要
  result_execution_id TEXT       -- 关联的最终 execution
  timeout_minutes INTEGER NOT NULL DEFAULT 120  -- 超时时间（默认 2 小时）
  created_at      INTEGER NOT NULL
  completed_at    INTEGER
```

### 用户在等待期间发新消息

```
场景分类:

  1. 新消息与当前委托无关:
     → 全局助手正常处理（或委托给其他团队）
     → 不影响正在进行的委托

  2. 新消息是追加/修改当前委托:
     "刚才那篇小红书，标题改成问句形式"
     → 全局助手识别为关联上一条委托
     → 发送 supplement 给目标负责人（追加指令）
     → 若任务已完成 → 创建新委托（带上上次结果作为上下文）

  3. 用户催促:
     "上次那个任务好了吗？"
     → 全局助手查询 delegation 状态
     → 回复进度: "内容团队正在处理中，已完成拆解，3 个子任务中 2 个已完成"

  4. 用户取消:
     "算了，不需要了"
     → 全局助手标记 delegation.status='cancelled'
     → 通知负责人: 取消执行
     → 清理队列中未开始的子任务
```

### 超时与失败处理

```
超时:
  · 默认 2 小时无结果 → delegation.status='timeout'
  · 通知用户: "内容团队的任务已超时，你可以: 1.继续等待 2.催促 3.取消"
  · 不自动取消（任务可能仍在进行，只是慢）

失败:
  · 团队执行失败（所有重试耗尽）→ delegation.status='failed'
  · 通知用户: "内容团队执行失败: {error}，你可以: 1.重试 2.换团队 3.放弃"
  · 提供一键重试（重新创建 delegation）

多团队协作:
  · 用户: "综合分析本周所有团队的数据"
  · 全局助手同时委托给多个团队 → 创建多条 delegation
  · 等所有 delegation completed → 全局助手汇总各团队结果
  · 部分超时: 用已完成的结果先回复，标注哪些团队未响应
```

## 二十、Session 生命周期管理

### Session 类型与生命周期

```
Session 类型:

  1. user_chat — 用户与 Agent 的对话
     · 创建: 用户首次向某 Agent 发消息
     · 结束: 用户手动关闭 / 空闲 30 分钟自动归档
     · 可恢复: 用户再次打开时加载历史消息
     · 每个 Agent 同时只有 1 个活跃 user_chat session（用户侧）

  2. execution — 任务执行上下文
     · 创建: job_queue claim 时
     · 结束: execution 完成/失败/取消时
     · 生存期: 与单次执行绑定
     · session_mode='reuse' 时: supplement/redo 复用同一 session

  3. chain — 链式执行上下文
     · 创建: chain 第一环开始时
     · 结束: 整条链完成或中断时
     · 跨多个 execution 共享上下文

  4. delegate — 委托上下文
     · 创建: 全局助手委托时
     · 结束: delegation 完成/超时/取消
     · 存储委托方信息，用于结果回传
```

### Session 与 Execution 的关系

```
关系模型:

  user_chat session:
    · 1 session : N executions（一次对话中可能多次执行）
    · 用户每发一条消息 = 触发一次 execution
    · 所有 execution 共享对话历史（messages 累积）

  execution session:
    · 默认 1:1（每次任务新建 session）
    · session_mode='reuse': supplement/redo 复用 → 1 session : N executions
    · reuse 时 messages 保留，Agent 有上下文续做

  并行限制:
    · 同一 Agent 同时只有 1 个 execution session（会话锁）
    · 但 user_chat session 可以与 execution session 共存:
        用户对话 session（暂停等待）+ 任务 execution session（正在执行）
    · 优先级: execution > user_chat
        若 Agent busy 且用户发消息 → 入 pending 队列，执行完后再处理
```

### 上下文压缩触发

```
压缩策略:

  触发条件（满足任一）:
    · session.message_count > 50
    · session.total_tokens > model_context_window × 0.6
    · 最早消息距今 > 24 小时

  压缩方式:
    · 调用 LLM 生成摘要（保留关键事实和决策）
    · 替换旧消息为 [compressed_summary] 系统消息
    · 保留最近 10 条消息原文（短期记忆）
    · 标记 session.compressed_at = now

  不压缩的场景:
    · execution session 执行中（压缩可能丢失关键上下文）
    · session.status = 'archived'（已归档的不再操作）
```

### Session 清理

```
定期清理（每日凌晨 5:00）:

  归档:
    · user_chat: 最后活跃 > 7 天 → status='archived'
    · execution: 已完成 > 3 天 → status='archived'

  删除消息:
    · archived session 的 messages: 保留 90 天后删除
    · 但 compressed_summary 永久保留（占空间小）

  不删除:
    · 有关联的未归档 task 的 session
    · 用户手动标记 "保留" 的 session
```

### 变更分类与即时性

### Provider 切换前置条件

```
将 Agent 从一种 provider 切换到另一种:

  前置检查:
    1. Agent 当前 status 必须为 'idle'（不能在执行中切换）
    2. 新 provider 的 API Key / 配置必须存在且有效
    3. 若新 provider 是外部 Runtime → 检查 CLI/服务可用（healthCheck）

  切换步骤:
    1. 验证新 provider 配置有效
    2. 更新 agent.provider + agent.config
    3. 清除 prior_session_id（旧 session 与新 Runtime 不兼容）
    4. 重置 prior_work_dir（可选，外部 Runtime 可能不复用目录）
    5. 保留 trust_level（不因切换降级）

  不可逆影响:
    · 旧 provider 的 session 数据仍保留（可查阅历史）
    · 新 provider 从零开始（无历史上下文）
    · 技能/记忆不受影响（是 system prompt 注入，与 provider 无关）
```

### 批量配置变更

```
场景: 用户想给整个团队所有 Agent 换模型（如 sonnet → opus）

  · changes: {model?, thinking_level?, ...}     — 修改什么

  限制:
    · 只允许修改"下次生效"的配置项（不允许批量改 status）
    · 每次最多影响 50 个 Agent（防止误操作）
    · 返回影响列表让用户确认后执行
```

## 二十三、并发冲突与一致性规则

### 审核 vs 手动操作冲突

```
冲突场景: Agent 输出正在等待审核 (review_status='pending')，
         用户同时在看板拖拽该任务到"已完成"

规则: 用户操作优先（用户 > Agent > 系统）

处理:
  1. 用户拖拽 → 立即更新 task.column = '已完成'
  2. 标记 execution.review_status = 'skipped_by_user'
  3. 取消进行中的审核 LLM 调用（如有）
  4. 写入 comment: "用户手动完成，跳过审核"
  5. 审核结果（如果已在路上）→ 丢弃，不覆盖用户操作

反向冲突: 审核通过瞬间用户拖到"待办"
  · 也是用户优先 → task 移回待办
  · execution 记录保持 approved（不撤销审核结果）
  · 任务可能需要重新执行
```

### 并发写入冲突检测

```
乐观锁机制（版本号）:

  tasks 表新增:
    version INTEGER NOT NULL DEFAULT 1  -- 每次更新 +1

  前端更新任务时:
    UPDATE tasks SET column_id=?, version=version+1
    WHERE id=? AND version=?  -- 检查版本号

  版本冲突时:
    · 返回 409 Conflict + 最新数据
    · 前端提示: "任务已被他人修改，请刷新"
    · 或自动刷新 + 重新应用用户操作（merge）

适用范围:
  · tasks（看板拖拽高频）
  · agent_executions（审核写入）
  · agents（多人同时编辑 Agent 配置）
  · 不需要: session_messages（只追加、不修改）
```

### 调度器 claim 原子性

```
已有设计（6.4）中 claim 使用 SQLite 事务保证原子性:

  BEGIN IMMEDIATE;
  UPDATE job_queue SET status='claimed', claimed_at=?
  WHERE id=? AND status='pending';
  COMMIT;

补充规则:
  · affected_rows = 0 → 已被其他轮询 claim，跳过
  · 超时回收: claimed_at + timeout_ms < now → 重置为 pending
  · 同一 Agent 不能同时被 claim 两个任务（会话锁检查在 claim 前）
```

### IPC 事件顺序保证

```
问题: 多个操作并发完成，IPC 推送顺序可能乱序（虽然概率低于网络场景）

解决:
  · 每个 workspace 的事件带递增 sequence_number
  · 渲染进程收到事件时检查 seq: 若跳号 → 通过 IPC invoke 请求补发缺失事件
  · 补发 IPC: window.api.invoke('events.since', { workspaceId, afterSeq })

  实现:
    · workspace_event_seq: Map<workspace_id, number>（内存递增）
    · 每次推送事件时: seq = ++workspace_event_seq[wid]
    · 事件持久化到 workspace_events 表（保留 24 小时用于补发）
```

## 二十四、Workspace Context 更新传播

### 传播规则

```
workspace.context 修改后:

  对正在执行的 Agent:
    · 不影响 — 当前执行使用的 system prompt 在启动时已组装完成
    · 不中断当前执行去注入新 context

  对下次执行的 Agent:
    · 自动生效 — Prompt 组装时从 workspace.context 实时读取
    · 无需重启 Agent 或手动刷新

  设计原则: 冻结快照模式
    · 执行开始时: 组装 system prompt（含当时的 context）→ 冻结
    · 执行过程中: context 变化不影响（保护 prompt cache）
    · 下次执行: 重新组装，自然获取最新 context
```

### Context 版本追踪

```
workspace.context 修改记录:

  workspace_context_history
    id           TEXT PRIMARY KEY
    workspace_id TEXT NOT NULL → workspaces.id
    content      TEXT NOT NULL  -- 变更后的完整 context
    changed_by   TEXT NOT NULL  -- user_id
    change_note  TEXT           -- 变更说明（可选）
    created_at   INTEGER NOT NULL

  用途:
    · 审计: 谁在什么时候改了 context
    · 回滚: 发现改错了可以恢复
    · 只保留最近 20 个版本（超过自动删最旧）

  不需要版本号字段:
    · context 变更频率低（不是高频字段）
    · 不需要乐观锁（修改 context 只在设置页，不会并发冲突）
```

## 二十五、外部 Runtime 异常处理

### 异常分类

```
外部 Runtime (CC/opencode/Hermes) 可能的异常:

  1. 进程启动失败 (spawn error)
     · 原因: CLI 未安装、PATH 找不到、权限不足
     · 处理: 立即标记 execution failed, error_type='permanent'
     · 前端: "Agent 运行环境不可用: {具体原因}"

  2. 进程崩溃 (exit code != 0, 无 execution_completed 事件)
     · 原因: 内部错误、OOM、段错误
     · 检测: 子进程 exit 事件触发
     · 处理: 标记 failed, error_type='transient', 可重试
     · 保留 stderr 输出用于诊断

  3. 超时 (timeout_ms 到达仍未结束)
     · 检测: setTimeout 触发
     · 处理: SIGTERM → 等 5s → SIGKILL
     · 标记: failed, error_type='timeout'
     · 收集已有的部分输出作为 checkpoint（如果有意义）

  4. 输出解析失败 (stdout 不符合 AgentEvent 格式)
     · 原因: Runtime 版本不兼容、输出格式变更
     · 处理: 跳过无法解析的行，记录 warn
     · 若所有输出都无法解析 → 标记 failed, error_type='permanent'
     · 提示: "Agent Runtime 输出格式不兼容，请检查版本"

  5. Token 用量未报告
     · 情况: 外部 Runtime 未在最终事件中报告 usage
     · 处理: 标记 input_tokens=NULL, output_tokens=NULL
     · 不影响任务状态（只影响费用统计精度）
     · 前端: Token 列显示 "—"

  6. 连接断开 (Hermes HTTP/WebSocket 中断)
     · 检测: 连接 error/close 事件
     · 处理: 重连 1 次（5s 后）
     · 重连成功 → 继续消费事件流
     · 重连失败 → 标记 failed, error_type='transient'
```

### 健康检查与预警

```
外部 Runtime 健康检查:

  触发时机:
    · 每 5 分钟定期检查所有已配置的外部 Runtime
    · Agent 执行前检查（快速 healthCheck）
    · 连续 3 次执行失败后强制检查

  检查方式:
    · claude_code: `claude --version` (spawn + 检查退出码)
    · opencode: `opencode --version`
    · hermes: GET {endpoint}/health
    · custom: GET {endpoint}/health (可选)

  健康状态:
    · healthy — 正常
    · degraded — 响应慢 (> 5s) 但可用
    · unavailable — 不可用

  告警:
    · unavailable → 通知用户: "{provider} 不可用，相关 Agent 无法执行"
    · 连续 3 次 degraded → 通知: "{provider} 响应缓慢"
    · Agent 执行时若 runtime unavailable → 直接标记 failed，不进入队列等待
```

## 二十六、文件系统权限模型

### 权限矩阵

```
目录权限（每个 Agent 执行时的文件访问范围）:

┌─────────────────────────────────────┬───────┬───────┬────────────────────┐
│ 路径                                 │ 读    │ 写    │ 说明                │
├─────────────────────────────────────┼───────┼───────┼────────────────────┤
│ data/workspaces/{wid}/shared/       │ ✅    │ ✅*   │ 团队共享（有条件写） │
│ data/workspaces/{wid}/agents/{self}/│ ✅    │ ✅    │ Agent 私有目录      │
│ data/workspaces/{wid}/agents/{other}/│ ❌   │ ❌    │ 其他 Agent 的目录   │
│ data/ 以外                          │ ❌    │ ❌    │ 系统目录            │
└─────────────────────────────────────┴───────┴───────┴────────────────────┘

* shared/ 写权限规则:
  · leader (1号负责人): 读写
  · 其他 Agent: 默认只读，可配置为读写
  · 配置: agent.config.shared_write_access = true/false
```

### 外部 Runtime 的文件限制

```
对外部 Runtime (CC/opencode) 的限制:

  内置 Runtime:
    · 工具层面实现: file_read/file_write 工具检查路径前缀
    · Agent 无法绕过（工具是平台提供的）

  外部 Runtime:
    · 无法在工具层面限制（外部 Runtime 有自己的文件工具）
    · 限制方式: 设置 workspacePath 为 Agent 私有目录
    · 外部 Runtime 的 CWD = agents/{self}/
    · shared/ 通过 symlink 提供只读访问:
        agents/{self}/.shared → ../../shared  (只读 symlink)
    · Docker 环境下可用 --read-only + tmpfs 强制

  文件操作审计:
    · 内置 Runtime: 每个 file_write tool_call 都记录
    · 外部 Runtime: 只能 diff workspacePath 前后变化
    · post-execution 检查: 执行前 snapshot → 执行后 diff → 记录变更文件列表
```

### 文件变更不需审核

```
设计决策: 文件操作不独立审核

  理由:
    · 文件操作是 Agent 执行的自然产物（代码生成、文档输出）
    · 上级审核 execution 输出时，已间接审核了文件变更
    · 逐文件审核粒度太细，会大幅增加审核成本

  替代方案:
    · shared/ 目录启用 git（可选）: 每次写入自动 commit
    · 用户可查看 shared/ 的变更历史（类似 git log）
    · 误删恢复: git revert 或从备份恢复

  危险操作保护:
    · 禁止删除 shared/ 根目录
    · 单次删除文件数 > 10 → 需用户确认
    · 单个文件 > 50MB → 拒绝写入
```

### 权限检查实现

```
中间件模式:

  每个 API 路由声明所需权限:
    route('/api/workspaces/:wid/delete', { requiredRole: 'owner' }, handler)
    route('/api/workspaces/:wid/agents/create', { requiredRole: 'admin' }, handler)
    route('/api/workspaces/:wid/tasks/create', { requiredRole: 'member' }, handler)

  权限中间件:
    1. 获取当前 session 的 user_id（本地进程内 session）
    2. 查 workspace_members: 该 user 在该 workspace 的 role
    3. role 权限比较: owner > admin > member
    4. 不满足 → 返回权限不足错误

  特殊情况:
    · 非 workspace 成员访问 → 404（不暴露 workspace 存在）
    · 全局助手操作不检查 workspace 权限（user 级）
    · 公开模板（team_templates.is_public=1）不检查权限
```
